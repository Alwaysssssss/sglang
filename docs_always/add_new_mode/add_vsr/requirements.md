## 2. 流式处理要求

流式处理指视频在推理过程中分块读取、处理、融合并增量写出；不能仅将整段视频载入内存后，分块调用模型就视为满足流式要求。

对齐时须沿用流式基线的时间窗口、空间 tile、重叠区融合、尾部处理、颜色校正和输出顺序语义。
`color_ref=global` 允许基线已有的颜色统计预扫描；流式处理不等于禁止预扫描。

**已确认：流式在第一阶段拆成「实现保留、验收后置」两半。**

- 实现上，流式仍是第一阶段的实现方式。时间窗口、空间 tile、重叠融合、尾部处理、颜色校正和输出顺序直接决定输出像素，因此这部分语义仍属第一阶段门禁，但由对齐验收（§4.1、§4.2）覆盖，不另设判据。
- 验收上，第一阶段不设内存门限，不需要固定分辨率、tile 和队列大小后跑不同长度的视频来验证内存不随帧数线性增长。该项连同视频长度和资源上限一并后置到加速阶段，与加速项一起测。
- 已确认接受其代价：若移植过程中内存退化为 O(帧数)，第一阶段不会发现。4K 下单帧输出为 `3*H*W` 字节（约 `24.9 MB`），该退化在长片上的表现是 OOM 而非变慢。

#### 4.1.2 容差来源：先实测下限

**2026-09-20 环境切换更新**：按用户要求，当前 VSR 默认运行栈已改为 torch2.10/cu126，保留 diffusers0.37。新环境的9组/649帧、单窗口逐阶段及原生pipeline均与原始swiftvr基线完全一致，见 [运行环境验收](runtime210.md)。下文的torch2.9.1差异和冻结容差是旧环境的历史测量，不是算法固有误差，也不限制当前环境取得零差异。

第一阶段两端使用同一套 diffusers 模型与同一套权重、同一型号 GPU（A100-80G），固有差异来自 torch
版本（基线 `2.10.0+cu126` 对 SGLang 侧 `2.9.1+cu128`）与 diffusers 版本（`0.36.0` 对 `0.37.0`）。
后者**无法消除**——`sglang` 的 `diffusion` extra 硬性要求 `diffusers==0.37.0`，不能把 SGLang 环境
固定到基线的 `0.36.0`。因此 `ε_torch` 按两项差异的合计实测值采纳。

**M0：写代码前的前置步骤。** 在 SGLang 环境下（`VE_SGLANG_PYTHON`）直接运行基线的

1. 验证 SGLang 环境可以跑通基线（`decord`、模型加载、cu128 下 bf16）；

3. 直接暴露 `0.97 / 25.0 / 2.5` 是否还有余量，避免到后期才发现门限不可达。

#### 4.1.3 采样点

依次验证以下边界，具体采样点以基线实际调用链为准：

1. 视频解码、resize、padding 和输入 tile。
2. VAE 编码及模型输入 latent。
3. DiT 输出及 VAE 解码结果。
4. 空间融合、时间融合与尾部提交。
5. 颜色校正、编码前输出帧及最终编码视频。

先验证单 tile，再验证多 tile 和多时间窗口，最后验证完整视频。

#### 4.1.4 配置分层

逐阶段细粒度对齐**不使用 4K 配置**：4K 下单个 chunk 张量为 `[1,3,33,3840,2176]` fp32 ≈ `3.3 GB`，
无法逐点 dump；`14×4` 个 tile 的差异也会淹没在噪声里，定位不到环节。

| 用途 | 配置 | 覆盖点 |
| --- | --- | --- |
| 单 tile / 单窗口 | `H×W = 320×640`，`T=33` | 采样点 1–5 的基线路径，单 tile 张量 `25 MB`，可逐点比对 |
| 多窗口融合 | 同上，`T=64` | 三窗口覆盖下的 `live_acc` / `live_w` 归一化语义 |
| 补齐路径 | `H×W = 336×656`，`T=33` | 非 32 倍数补齐与 tile 栅格 |
| 时间反射补齐 | `H×W = 320×640`，`T=10` | `T < tile_t` 的反射扩展与尾部裁剪 |
| 单帧分支 | `H×W = 320×640`，`T=1` | `reflect_pad_time` 的单帧重复分支（`idx = [0] * target_t`） |
| 完整验收 | `3840×2160`，`T=53` | 交付物门限（§4.2） |

#### 4.1.5 数值失败的归类

数值失败必须报告**差异集中在哪里**，每类直接指向一条代码路径：

| 差异形态 | 指向 |
| --- | --- |
| 所有帧、所有位置近似常数偏置 | latent 归一化或颜色校正的施加次数与顺序（§7-2、§7-5） |
| 只在 tile 接缝处 | 空间 feather 权重、外边界不衰减语义 |
| 只在时间窗口接缝处 | 时间权重与 retire 归一化（§7-4） |
| 只在最后一两个窗口 | 尾窗回退 `compute_tile_positions`、`emit_end` 算术 |
| 只有某个颜色通道整体缩放 | AdaIN 的 mean/std 取值范围（是否含 overlap 区） |

### 4.2 最终视频验收

验收分两层，两层的判据与角色不同：**编码前 uint8 帧是算法对齐的主判据；编码后 mp4 是交付物门限与报告产物。**

#### 4.2.1 编码前 uint8 帧（算法对齐主判据）

比对两端 `to_uint8_hwc` 的输出：形状 `[T, H, W, 3]`、dtype `uint8`、范围 `0..255`、帧数与帧序一致。
该层不含编码器噪声，差异是纯算法信号，容差按 `ε_torch` 设定（§4.1.2），可显著紧于视频门限。
须记录逐帧 `MAE` / `MSE` / 最大绝对误差及其分布，供 §4.1.5 的差异归类使用。

分层的理由：mp4 是**有损代理**，yuv420p 色度下采样与 `crf=5` 会在边缘放大差异、同时在平坦区掩盖差异，
因此只靠 mp4 无法区分「算法差异」与「编码器放大了噪声」。两层同时保留即可各自定位。

#### 4.2.2 编码后 mp4（交付物门限）

用户已确认采用 [VideoEdit 实际对齐文档](../../video-edit-compare/env.md) 使用的 case-specific
实测门限，**不使用** [VideoEdit 迁移文档 §11.5](../add_videoedit_diffusers/README.md#115-reference-逐帧对齐)
中命名为 `strict` 的 `0.95/60/5.0` 档：

| 参数 | 阈值 |
| --- | --- |
| `min_ssim` | `0.97` |
| `max_mse` | `25.0` |
| `max_mae` | `2.5` |
| `max_failed_frame_ratio` | `0.0` |
| `allow_frame_count_delta` | `0` |

每帧必须同时满足 `SSIM >= 0.97`、`MSE <= 25.0`、`MAE <= 2.5`，不允许失败帧。
沿用 VideoEdit 比较器的计算口径：8-bit RGB 范围为 `0..255`，MSE/MAE 在 RGB 上计算，SSIM 使用其灰度实现。
保留逐帧结果、失败帧索引和汇总统计，包括 `ssim_min`、`mse_max`、`mae_max`；PSNR 和最大绝对误差作为诊断指标记录。

VSR 以完整生成画面为验收对象：不沿用 VideoEdit 因参考帧保存策略产生的丢首帧例外，不通过 resize 或截断掩盖输出差异。
结构一致性检查见 §4.3，须在运行比较器之前完成。

#### 4.2.3 编码器确定性检查

额外做一次检查：把同一批 uint8 帧喂给两端各自的 writer，比较产出的 mp4 是否一致。
该检查确立「mp4 差异 ⇒ 帧差异」这一推理成立；若编码器本身不确定，§4.2.2 的门限就不可解释。
检查只做一次，不作为每次验收的常规项。

**M1 实测结果（2026-09-18）：通过，且附带验证了 dump 工具本身。**
把 A1 基线 dump 的 53 帧分别用两个环境编码，产物 md5 相同（`4e6576d4c594e8eadd3ef8c8a453281a`），
且与基线的两次实跑产物（`M0_reference_swiftvr_a.mp4`、`M1_ref_swiftvr.mp4`）**也完全相同**。
后者证明 dump 抓到的帧就是基线真正交给编码器的那批，是对 §4.2.4 包装脚本的端到端验证。

#### 4.2.4 实现方式

基线仓库按 `environment.md` §6 为只读，因此两层的 dump 都通过一个**包装脚本**完成：
`sys.path` 引入 `VSR_REPO` 后 monkey-patch `_restore_window` / `tiled_restore_rect` /
`match_color_to_stats` 等函数，不修改基线源码。该包装脚本与 §4.1.4 的逐阶段对齐脚本是同一份，
最终帧的 dump 只是在同一包装中多加一个采样点。

### 4.3 视频结构一致性（前置硬检查）

在运行比较器之前完成，结果单独报告。**不交给 `compare.py` 代劳**，原因：

- 两端形状不一致时 `compare.py` 会执行 `cv2.resize(candidate, (ref_w, ref_h))`（以参考为准），
  分辨率不一致不但不会被发现，还会被抹平成一个很高的 SSIM；
- `compare.py` 用 `cv2.VideoCapture` 逐帧读，不读时间戳与容器帧率，帧率不一致会静默通过；
- 帧数差超过 `allow_frame_count_delta` 时 `compare.py` 直接 `raise ValueError`（且 `main()` 未捕获），
  表现为 traceback 与退出码 1，与「门限不过」无法区分。

| 检查项 | 判据 |
| --- | --- |
| 分辨率 `(W, H)` | 逐帧一致 |
| 帧数 | 差 `0`，即 `allow_frame_count_delta = 0` |
| 帧率 | 两端一致 |
| 帧序 | 零偏移最优 |
| `drop_*_first_frame` | 必须关闭 |

帧数：VSR 基线没有丢帧策略，`stream_restore` 以 `emitted != T` 断言输出帧数等于源帧数，因此 `delta = 0` 无争议。

帧序：对两端逐帧计算均值与标准差序列，在 `lag ∈ [-2, +2]` 内取最优对齐；最优 `lag` 不为 `0` 即判定帧序或帧数异常。
仅靠逐帧指标无法区分「整体错位」与「算法差异」，故需显式判别。

### 5.2 后置项与加速排序

**HTTP 服务：第一阶段明确后置。** 与 §5 的交付物一致（pipeline + CLI + 验收报告）。VSR 的输入输出都是
磁盘上的视频文件、流式、单次运行以分钟计；服务化需要上传/下载、异步任务模型、进度上报、准入控制与
存储后端——VideoEdit 为此新增了 `dualservice_gateway` / `dualservice_store` / `request_audit` /
`progress` / MinIO 协议等一整套，这些对算法对齐没有贡献。

**架构约束（现在就要满足，否则服务化需返工）**：流式核心 `runtime/vsr/stream.py` 不得依赖 CLI 参数对象，
应接受明确的几何 / 队列 / IO 参数，输入输出路径经 `Req` / 采样参数传入，使 CLI 与将来的 serve 都能包装它。

**加速排除项**（这几项比加速项本身更容易被误选）：

| 排除 | 理由 |
| --- | --- |
| TeaCache / Cache-DiT | 面向多步采样的跨步特征复用；VSR 每 tile 只做一次 DiT 前向，没有「步」可缓存 |
| 改 `tile_t` / `tile_h` / `tile_w` | 改变模型看到的上下文与 token 数，偏离训练配置，属于改语义而非加速 |
| 减小 `temporal_overlap` | `33/28` 的冗余只有约 `1.18×`，收益上限约 `15%`，却改变融合结果 |

**加速排序**（逐项叠加，每项单独验证结果并记录性能变化）：

| 序 | 加速项 | 理由 |
| --- | --- | --- |
| 2.1 | 同一 chunk 内空间 tile 批处理 | 56 个 tile 完全独立，基线为串行循环；单 tile 的 DiT 仅 `1800` token，GPU 利用率低。56 个 tile 的 latent 合计 `[56,48,9,20,40]` ≈ `39 MB` bf16，显存充裕 |
| 2.2 | 多 GPU 按 tile 数据并行 | tile 间无依赖；8 × A100 上每卡多存一份 5B 权重（bf16 约 `10 GB`）可行 |
| 2.3 | `torch.compile` | DiT 输入形状固定（`1800` token），无动态形状问题 |
| 2.4 | 量化（fp8） | 数值影响最大，需重跑逐帧比较，故置于最后 |

§2 后置的**内存验收与 2.1 / 2.2 合并进行**：这两项最可能把内存搞爆（批处理会同时按住多个 tile 的中间量），
与加速项一起测是自然的。

以下为 2026-09-18 对照两端源码核实的结果，记录在此以免遗漏；前两项在第一阶段用 diffusers 模型可绕开，
但是第二阶段切原生模型的**前置验证项**。

1. **VAE decoder 权重能否直接加载。** `vae_decoder_ema.pt` 是裸 state_dict，顶层键为
   `conv_in` / `mid_block.{attentions,resnets}` / `up_blocks.0-3` / `norm_out.gamma` / `conv_out`，共 108 个键，
   命名来自 diffusers 模块路径。SGLang 的 `WanDecoder3d` 存在同名子模块（`conv_in` / `mid_block` / `up_blocks`），
   但 `norm_out.gamma` 在 `runtime/models/vaes/wanvae.py` 中未出现，是否需写参数名映射**待实测**。
2. **latent 归一化重复施加。** 基线在 `Stage3VAE.encode/decode` 中显式做 `(z-μ)/σ` 与反归一化（μ/σ 取自
   `vae.config.latents_mean/latents_std`）；SGLang 的 `AutoencoderKLWan` 自带 `latents_mean` / `latents_std` /
   `shift_factor`，pipeline config 另有 `get_decode_scale_and_shift` 回调。两边同时施加会导致整体偏色。
3. **无文本编码器。** 基线的 `encoder_hidden_states` 是 `torch.zeros(1, 1, 4096)` 零张量，不是空字符串经文本编码器
   得到的 embedding，且管线不加载任何文本编码器。因此 pipeline 的 `_required_config_modules` 须去掉
   `text_encoder` / `tokenizer`，且不能走标准的文本编码与条件构造路径。
4. **时序融合必须按归一化语义实现。** 流式基线采用未归一化累加（`live_acc` / `live_w`）在帧退出时除以权重和；
   整段视频路径用的是"双侧 cross-fade"。两者在有帧被 3 个及以上窗口覆盖时**不相等**（`T=64`、`tile_t=33`、
   `temporal_overlap=5` 即触发）。实现须照搬归一化语义，不能按 cross-fade 重写。
5. **颜色校正的施加位置与覆盖范围。** `global` / `chunk` 校正必须在时间融合**之前**、按 chunk 施加，且此时
   `restored` 已被裁剪为 `[:tile_t, :target_h, :target_w]`，统计量覆盖整块（含随后会被融合掉的 overlap 区）。
   顺序或覆盖范围改变都会改变输出。
6. **全局颜色预扫描是基线语义。** `color_ref=global` 会在正式流式前额外解码采样帧（默认 64）计算参考统计量，
   `color_ref_samples=0` 表示逐帧。这不是可选优化。
7. **最终量化是截断，不是四舍五入。** `to_uint8_hwc` 走的是
   `(x*0.5+0.5).clamp(0,1)` → `(x*255).clamp(0,255)` → `.to(torch.uint8)`，而 torch 的浮点转 `uint8`
   是**向零截断**（实测 `0.6 → 0`、`1.6 → 1`、`254.9 → 254`；四舍五入则为 `1`、`2`、`255`）。
   若 SGLang 侧改用 `round` / `np.round` / cv2 的转换约定，会造成约半数像素系统性差 1 个灰阶，
   即 `MAE ≈ 0.5`、`MSE ≈ 0.5`，直接占掉 `max_mae = 2.5` 的约 20%。必须在实现中照搬截断语义。
