# 转正答辩：视频编辑模型推理加速与服务化上线

## 1. 项目一句话总结

我负责将视频编辑模型从“算法可运行”推进到“业务可使用”：围绕推理耗时、显存占用和生产服务能力，对模型推理链路进行了系统性重构与优化，最终实现 **推理性能提升 6 倍、显存从 60 GB 降至 12 GB（降低 80%）、稳定 API 服务上线，服务稳定性达到 95%**。

这项工作的核心不是单点调优，而是完成了从算法工程、推理引擎、资源优化到在线服务的端到端闭环。

## 2. 背景与核心挑战

原始视频编辑模型面向实验验证，存在三个阻碍业务落地的问题：

1. **速度慢**：视频扩散模型需要对时空 Token 进行多步去噪，DiT 是绝对耗时瓶颈；长视频还需要重复执行多个窗口，业务等待时间过长。
2. **显存高**：模型权重、中间激活、Attention、VAE 编解码和全量视频帧同时占用显存，峰值约 60 GB，硬件成本高且无法处理更大分辨率输入。
3. **缺少服务化能力**：原始调用依赖本地文件与人工配置，缺乏异步任务、统一协议、Mask JSON、对象存储、回调、限流和异常兜底，无法稳定接入业务系统。

我的目标是：在保证编辑效果和输出帧语义正确的前提下，把模型做成“跑得快、放得下、接得上、稳定运行”的生产服务。

## 3. 我具体做了什么

### 3.1 完成模型在 SGLang 推理框架中的工程化集成

- 新增独立的 `VIDEO_EDIT` 任务和 Wan VideoEdit Pipeline，避免把视频编辑强行复用普通文生视频/图生视频路径。
- 将原始单体 Pipeline 拆成参数校验、文本编码、条件编码、Latent 初始化、时间步准备、DiT 去噪、VAE 解码、窗口后处理等阶段，便于定位性能瓶颈和独立优化。
- 建立统一的采样参数、模型配置、CLI 与 Serve 参数体系，使编译、并行、Offload、Cache、Attention Backend 等能力可以按部署环境组合启用。
- 增加阶段耗时与显存峰值统计，通过 profiling 确认 DiT Denoising 是主要瓶颈，形成“测量—定位—优化—回归”的性能迭代闭环。

### 3.2 推理性能优化：端到端提升 6 倍

我采用组合优化，而不是依赖单一手段：

#### 结构性减算：全局 Mask BBox 裁剪

- 扫描整段 Mask 得到全局编辑区域，只对需要修复的局部区域执行 VAE 编码、DiT 去噪和 VAE 解码。
- 对 BBox 做最小尺寸扩展、Padding 和 16 对齐，既满足模型输入约束，又避免全分辨率计算。
- 推理完成后通过 Paste-back 和羽化边缘贴回原视频，保留非编辑区域的原始画质。

该优化直接减少空间 Token 数，是性能和显存收益最大的结构性手段之一，并且编辑区域越小，收益越明显。

#### 长视频窗口化与流水线化

- 针对模型固定窗口限制，将长视频拆分为 81 帧窗口；尾部不足时采用反射补帧，补帧只参与推理、不写入最终结果。
- 支持窗口 Overlap、参考帧丢弃、窗口结果回填与全局帧序对齐，解决长视频边界和帧数一致性问题。
- 将视频读取改造成流式解码，并在当前窗口推理时预取下一窗口，实现 IO 与 GPU 计算重叠。

#### 编译与算子优化

- 接入 `torch.compile`，对常驻服务中的固定 Shape DiT 计算图进行融合和编译；通过 Warmup 将首次编译成本移出稳定态请求。
- 接入 FlashAttention 等高性能 Attention Backend，降低时空 Attention 的访存和计算开销。
- 使用 BF16/Autocast，发挥 Tensor Core 吞吐并减少激活占用。
- 对 VAE 开启 Tiling，降低高分辨率解码峰值；通过阶段化执行及时释放不再使用的中间 Tensor。

#### 多卡并行

- 接入 Sequence Parallel / Ulysses 并行，将视频时空 Token 沿序列维度切分到多张 GPU。
- 在各卡完成局部 Transformer 计算后聚合序列结果，降低单卡计算压力并提升吞吐。
- 针对并行度、Attention Backend、输入 Shape 和通信开销进行组合验证，避免“卡数增加但通信抵消收益”。

仓库实测中，100 帧任务从单卡 Offload 的 1113.29 秒降至双卡 SP2 + No-offload + FlashAttention 的 345.79 秒，约 **3.22 倍**；在此基础上叠加局部裁剪、编译、Cache、量化等整体方案，业务口径端到端达到 **6 倍加速**。

#### Cache 与去噪步数优化

- 接入 TeaCache/Cache-DiT，利用相邻扩散步骤特征变化较小的特点，命中时复用 Residual，跳过部分 Transformer Block 计算。
- 实现 Dynamic CFG：前 15 步执行正负双分支，后 5 步 CFG 回落至 1，仅执行正分支；20 步场景下 DiT Forward 从 40 次降至 35 次，理论减少 12.5% Forward。
- Cache 采用请求级开关并配套质量回归，确保性能收益不以不可控的生成质量下降为代价。

#### 量化

- 打通 VideoEdit DiT 的量化配置透传，使 Self-Attention、Cross-Attention、FFN、输出投影以及条件投影均能正确加载量化方法。
- 支持 FP8/W8A8 等部署方向，降低权重显存和矩阵乘带宽；对未量化模块、Scale、Prefix、Checkpoint 兼容性进行检查。
- 对量化与 TP/SP、Cache、Offload 的组合单独回归，避免 Shape 整除、Kernel 兼容或精度问题。

### 3.3 显存优化：60 GB 降至 12 GB，降低 80%

我把显存问题拆成权重、激活、视频数据和解码峰值四类治理：

- **权重侧**：通过 BF16/FP8 量化减少模型常驻权重；按部署档位启用模型/层级 Offload。
- **激活侧**：BBox 裁剪减少空间 Token，窗口化限制时间维度峰值，Sequence Parallel 分摊单卡激活。
- **数据侧**：流式解码和窗口预取替代全量帧常驻，只保留当前窗口和有限预取 Buffer。
- **VAE 侧**：启用 Tiling/分块解码，避免高分辨率视频在最终 Decode 阶段出现瞬时 OOM。
- **生命周期侧**：按 Pipeline Stage 管理中间变量，窗口提交后及时释放临时 Tensor，并建立峰值显存监控。

最终峰值显存由 **60 GB 降至 12 GB**，减少 **48 GB，降幅 80%，资源效率提升 5 倍**。这意味着原先需要高显存卡的任务可以下沉到更低成本的部署规格，也为更大图片、更高分辨率和更长视频留出了空间。

### 3.4 服务化上线：从本地脚本到稳定 API

- 提供 `/v1/videos/repairs` 统一接口，兼容 snake_case/camelCase，收敛业务默认参数。
- 支持本地路径、URL、Mask 视频及 Mask JSON/COCO 等输入形式，并完成 Mask 校验、BBox 计算、膨胀与缩放等预处理。
- 支持参考图自动插入首帧，同时插入对应全量 Mask；输出时自动去掉参考帧，保证业务输入输出帧数一致。
- 接入 MinIO/S3：下载视频、Mask、参考图，推理结束后上传结果并生成对象 Key，消除业务方对本地路径的依赖。
- 建立异步任务队列和双服务网关，可在 Normal/DMD 模型间路由，提供忙碌保护、排队、任务状态和并发控制。
- 实现成功/失败终态回调，统一 `{code, message, reason}` 协议；保证异常也能回传明确原因，避免业务任务悬挂。
- 增加健康检查、启动/停止/状态脚本、请求审计、敏感字段脱敏、分阶段日志和冒烟/排队测试。
- 最终向业务方提供稳定 API，服务稳定性达到 **95%**。

## 5. 产生的业务价值

### 5.1 从“不可用”变成“可用”

6 倍加速显著缩短用户等待时间，使视频编辑从离线实验能力转为可进入业务流程的在线能力；异步 API、回调和对象存储让业务方无需理解模型部署细节即可接入。

### 5.2 降低 GPU 成本，提高资源利用率

显存下降 80%，使模型可以部署在更低显存、更低成本的 GPU 上；在同等集群资源下，可以容纳更多实例或处理更大分辨率输入。若任务量为 `N`，单次 GPU 时成本可近似随 6 倍加速降至原来的 `1/6`（实际还需结合卡型、并行数和利用率核算）。

### 5.3 扩大业务边界

长视频窗口化、局部编辑、流式解码与更低显存共同扩大了可处理的视频长度和分辨率；Mask JSON、参考图和 Paste-back 支持更精确、更自然的局部编辑，满足更多产品形态。

### 5.4 降低接入和运维成本

统一协议、合理默认值、S3/MinIO、终态回调和错误码降低了业务接入成本；健康检查、请求审计、敏感信息脱敏、排队与限流提升问题定位效率和服务可维护性。

### 5.5 沉淀可复用的推理优化方法

形成了“Profiling 定位瓶颈 → 减少计算量 → 算子/编译优化 → 并行与量化 → 显存治理 → 服务稳定性”的完整方法论，可复用到其他视频生成、视频修复和扩散模型项目。

## 6. 建议的答辩讲述方式

### 90 秒版本

我负责视频编辑模型的推理加速和服务化。项目最初存在三个问题：推理慢、显存约 60 GB、只有本地算法脚本，无法直接接入业务。我先通过 Profiling 确认 DiT 去噪是主要瓶颈，然后从减算、执行效率和并行三个层面优化：通过 Mask 全局 BBox 只计算编辑区域，通过窗口化和流式预取处理长视频，通过 BF16、FlashAttention、torch.compile、Dynamic CFG 和 Cache 降低单步成本，再通过 Sequence Parallel 和量化进一步提升吞吐。同时用分层 Offload、VAE Tiling和中间变量生命周期管理控制显存。最终推理速度提升 6 倍，显存从 60 GB 降到 12 GB。最后我把能力封装成异步 API，补齐 Mask JSON、参考图、MinIO/S3、队列、回调、错误码、审计和健康检查，稳定性达到 95%，真正把模型从实验阶段推进到业务可用阶段。

## 7. 评委可能追问及回答要点

### 为什么是 6 倍，分别由什么贡献？

6 倍是业务最终配置相对原始基线的端到端组合收益，不应简单相加各单项比例。BBox 裁剪负责减少问题规模，FlashAttention/编译/BF16 优化单次计算，Dynamic CFG/Cache 减少 Forward，多卡 SP 分摊计算，流式预取减少 IO 等待。答辩时建议展示同输入、同参数、同硬件或按 GPU 数归一化的逐级消融表。

### 60 GB 到 12 GB是否牺牲了效果？

窗口化、流式解码、Offload 和 VAE Tiling主要改变执行方式，不改变模型语义；BF16/量化和 Cache 可能影响数值或画质，因此通过固定 Seed、逐帧 SSIM/感知指标和人工 Case 回归控制质量。仓库已有 162 帧逐帧相似度对比材料，可作为质量证据。

### 为什么稳定性是 95%，剩余 5%是什么？

建议按真实统计口径回答，例如 `成功终态任务数 / 已受理任务数`，并明确统计周期、样本量及失败分类。剩余失败应拆为输入源下载、非法 Mask、对象存储/回调网络、超时/OOM和服务异常；强调已经通过校验、重试、限流、错误回调和监控降低不可控失败。

### 你个人最核心的贡献是什么？

不是简单调用现成框架，而是打通了三层：第一，理解并重构视频编辑模型的长视频和局部编辑推理流程；第二，围绕瓶颈组合使用并验证编译、算子、并行、Cache、量化和显存治理；第三，把算法封装成具备存储、回调、队列、审计和异常闭环的生产服务。

## 8. 指标口径提醒

- “6 倍”应注明测试视频、分辨率、帧数、步数、卡型、卡数、是否包含 Warmup、是否包含下载上传。
- “12 GB”应注明是 `max_memory_allocated`、`max_memory_reserved` 还是监控峰值，以及单卡还是多卡单卡峰值。
- “95%”应注明统计周期、任务数和公式。若目前只有阶段性验收数据，表述为“验收期任务成功率/服务稳定性 95%”。
- 仓库历史记录中存在约 14.2 GB allocated 的单卡 Offload Case；答辩采用 12 GB 时，应使用最终业务版本的监控截图或 Perf JSON作为证据，避免不同版本和口径混用。
