FlowCut 下游服务接口规范

本文档面向下游处理服务的开发者。FlowCut 作为调度层，负责任务创建、排队、分发和状态管理。下游服务只需按本规范实现接口，即可与调度层对接。

开发者实现清单

  • 实现任务分发接口
    • 提供一个 POST 接口（例如 /generate），用于接收 FlowCut 分发的任务。
    • 在 30 秒内同步响应请求。
    • 正确解析请求体中的 taskId、callbackUrl、minioConfig 及业务参数。
    • 根据处理意图返回特定的 code：
      • code: 0 — 成功接受任务，将异步处理。
      • code: 1 — 业务参数错误或资源不可用，任务永久失败。
      • code: 2 — 当前并发已满，任务稍后重试。
  • 实现异步任务处理
    • 在接受任务后，将实际处理逻辑放入后台异步执行。
  • 实现结果回调逻辑
    • 任务处理完成后（无论成功或失败），必须向 callbackUrl 发送 POST 请求。
    • 回调请求体中需包含 status（succeeded 或 failed）及可选的 reason 和 output。
    • （可选）可在处理过程中多次回调上报 running 状态和 progress。
  • 实现服务并发管理
    • 服务需自行维护并发计数，当达到上限时，对新的 /generate 请求返回 code: 2。

一、概述

1.1 交互模型

                                    异步回调
FlowCut 调度层 ──POST──> 下游服务 ──────────> FlowCut 回调接口
  (同步请求)               (接受任务)            POST /tasks/{id}/callback
                        后台异步处理...               (报告结果)

交互分为两个阶段：

阶段方向协议时效要求
任务分发 调度层 → 服务 POST /generate 同步请求 服务必须在 30 秒内响应
结果回报 服务 → 调度层 POST /tasks/{id}/callback 处理完成后调用，无严格超时

1.2 关键约束

  • 服务接受任务后需异步处理，完成后必须主动调用回调接口通知调度层。
  • 服务需自行管理并发，超出上限时应返回特定业务码拒绝新任务。

二、任务分发接口（下游服务须实现）

2.1 接口定义

可使用 /generate 或其他路由路径。

POST /generate
Content-Type: application/json

2.2 请求体

调度层会将用户创建任务时提交的 input JSON 字符串解析后，注入以下系统字段，作为请求体发出：

{
  "taskId":      "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timeout":     300,
  "callbackUrl": "http://flowcut.example.com/tasks/a1b2c3d4-.../callback",
  "minioConfig": {
    "endpoint":    "minio.example.com:9000",
    "bucket_name": "flowcut",
    "access_key":  "admin",
    "secret_key":  "******",
    "secure":      false,
    "region":      "us-east-1"
  },
  "image_url":   "https://example.com/input.jpg",
  "mask_url":    "https://example.com/mask.png"
}

字段说明

字段类型来源说明
taskId string 调度层注入 任务唯一标识（UUID），回调时需携带。必须处理
timeout int 调度层注入 超时秒数（0 表示默认 300 秒）。服务应据此控制处理时长。建议处理
callbackUrl string 调度层注入 回调地址。服务处理完成后必须向此 URL 发送结果。必须处理
minioConfig object 调度层注入 MinIO 存储配置。仅在调度层配置了 MinIO 时存在。可选
image_url string 用户 input 业务参数示例，实际字段取决于上游调用方。必须处理
mask_url string 用户 input 业务参数示例，实际字段取决于上游调用方。必须处理
... any 用户 input 用户创建任务时传入的所有 input 原始参数。

minioConfig 详细结构

字段类型说明
endpointstringMinIO 服务地址（host:port）
bucket_namestring存储桶名称
access_keystring访问密钥
secret_keystring密钥
securebool是否使用 HTTPS
regionstring存储区域

2.3 响应规范

服务收到请求后，同步返回一个 JSON 响应，通过 HTTP 状态码和 code 字段共同表达处理意图。

2.3.1 接受任务（成功）

code: 0 — 成功接受
// HTTP/1.1 200 OK
{
  "code": 0,
  "message": "ok"
}
  • code 必须为 0（整数）。
  • message 可自定义。
  • 表示服务已接受任务，将进入异步处理。
注意
返回 code: 0 后，服务必须通过回调接口回报最终结果，否则任务将停留在 running 状态。

2.3.2 业务失败（永久失败）

code: 1 — 业务失败
// HTTP/1.1 200 OK
{
  "code": 1,
  "message": "invalid mask image format"
}
  • code 必须为 1（整数）。
  • message 为失败原因描述，将记录到任务的 reason 字段。
  • 适用场景：输入参数错误、资源不可访问、业务规则不通过等。

2.3.3 并发限制（可重试拒绝）

code: 2 — 并发限制
// HTTP/1.1 200 OK
{
  "code": 2,
  "message": "A task is running."
}
  • code 必须为 2（整数）。
  • message 可自定义。
  • 表示服务当前并发已满，无法接受新任务。
  • 调度层收到此响应后，任务保持 pending 状态，约 5 秒后自动重试。
重要
这是服务向调度层传递「我很忙」信号的唯一正确方式。不要通过返回 HTTP 503 或其他状态码来表达并发限制。

2.3.4 响应总览表

场景HTTP Statuscode调度层行为任务状态变化自动重试
成功接受2000 任务进入运行态pending → running-
业务失败2001 任务标记为失败pending → failed否
并发限制2002 任务等待后重试pending（不变）是，约 5 秒后
服务不可用503(忽略) 任务等待后重试pending（不变）是，约 5 秒后
其他 5xx500/502/...(忽略) 任务标记失败 + 端点不健康 + 告警pending → failed否
4xx 错误400/404/...(忽略) 任务标记失败pending → failed否
响应体非 JSON200- 任务标记失败pending → failed否

2.3.5 重要提醒

HTTP 503 特殊语义
调度层将 503 视为暂时不可用（可重试），且不会标记服务为不健康。如需表达「当前忙」，优先使用 code: 2。
HTTP 5xx 严重后果
除 503 外的任何 5xx 响应会导致服务被标记为不健康（跳过后续调度），并触发告警。请确保服务稳定时不要返回 5xx。
  1. 响应体格式：HTTP 200 时，响应体必须是合法 JSON（至少包含 code 字段），否则任务直接失败。
  2. code 字段类型：必须为数字类型（整数 0/1/2），不是字符串。

三、回调接口（下游服务调用调度层）

3.1 接口定义

服务在异步处理任务过程中或完成后，必须向请求体中携带的 callbackUrl 发送 POST 请求。

POST {callbackUrl}
Content-Type: application/json

其中 {callbackUrl} 格式为：http://<flowcut-host>/tasks/<taskId>/callback

3.2 请求体

{
  "status":   "succeeded",
  "progress": 100,
  "reason":   "",
  "output":   "{\"result_url\":\"https://minio.example.com/outputs/result.jpg\",\"duration\":45}"
}

字段说明

字段类型必填说明
statusstring 是 任务结果状态，合法值见下表。
progressnumber 否 处理进度，范围 0.0 ~ 100.0。
reasonstring 否 状态原因说明。成功时可空，失败时应填写错误描述。
outputstring 否 处理结果，建议为 JSON 字符串。成功时填写结果数据，失败时可省略。

status 合法值

status含义使用场景
succeeded处理成功任务正常完成
failed处理失败任务执行出错、资源异常等
running处理中上报中间进度（配合 progress 字段）

典型调用时机

1) 处理成功

{
  "status":   "succeeded",
  "progress": 100,
  "reason":   "",
  "output":   "{\"result_url\":\"https://storage.example.com/out/result.jpg\"}"
}

2) 处理失败

{
  "status":   "failed",
  "progress": 0,
  "reason":   "GPU out of memory during inference",
  "output":   ""
}

3) 进度上报（可选）

{
  "status":   "running",
  "progress": 45.5,
  "reason":   "processing frame 23/50",
  "output":   ""
}
进度上报不是必须的。如果服务支持，可在处理过程中多次调用回调接口。

3.3 响应

回调接口无需认证，成功时返回：

{
  "code": 0,
  "msg":  "callback processed"
}

服务无需关心回调的响应内容，只需确保 HTTP 请求发送成功即可。

3.4 重置任务为 pending（高级用法）

在特殊场景下（如服务内部 OOM 导致任务异常中断），服务可通过回调将任务重置为 pending 状态，触发调度层重新分发：

{
  "status":   "pending",
  "progress": 0,
  "reason":   "task reset due to OOM, requesting re-dispatch",
  "output":   ""
}
约束
仅当任务当前处于 pending、running 或 failed 状态时允许重置。succeeded、paused、canceled 状态的任务不允许被重置为 pending。

四、并发管理

4.1 服务侧并发控制

服务必须自行维护并发计数，在接收 POST /generate 请求时：

  1. 检查当前运行任务数是否已达并发上限。
  2. 未达上限 → 接受任务，计数 +1，返回 code: 0。
  3. 已达上限 → 拒绝任务，返回 code: 2。
  4. 任务处理完成后（无论成功失败），计数 -1。

5.2 自检清单

#检查项说明
1POST /generate 接口可达调度层配置的 URL 能正确路由到服务。
2请求体能正确解析兼容 taskId、timeout、callbackUrl、minioConfig 及业务字段。
3成功时返回 {"code": 0, ...}HTTP 200 + JSON。
4业务失败时返回 {"code": 1, ...}HTTP 200 + JSON。
5并发满时返回 {"code": 2, ...}HTTP 200 + JSON。
6异步处理后回调 callbackUrl成功/失败都必须回调。
7回调体包含 status 字段值为 succeeded / failed。
8并发控制逻辑正确超限时拒绝，完成后释放。
9TCP 端口可达调度层健康检查（每 30 秒 TCP Dial）能连通。
1030 秒内返回同步响应超时会被视为网络错误并重试。

六、附录：Mock 服务参考实现

以下是 FlowCut 内置的 Mock 服务代码，可作为实现参考：

// POST /generate
func HandleGenerate(c *gin.Context) {
    var req struct {
        TaskID  string `json:"taskId"`
        Timeout int    `json:"timeout"`
    }
    // 参数错误 → code: 1
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(200, gin.H{"code": 1, "message": "invalid request"})
        return
    }

    // 并发已满 → code: 2
    if !CanStartTask() {
        c.JSON(200, gin.H{"code": 2, "message": "A task is running."})
        return
    }

    // 接受任务 → code: 0
    IncrementRunningCount()
    go processTaskAsync(req.TaskID, req.Timeout)
    c.JSON(200, gin.H{"code": 0, "message": "ok"})
}

// 异步处理完成后回调
func processTaskAsync(taskID string, timeout int) {
    defer DecrementRunningCount()

    // ... 执行实际处理 ...

    // 回调通知调度层
    callbackURL := fmt.Sprintf("%s/tasks/%s/callback", flowcutHost, taskID)
    body := map[string]interface{}{
        "status":   "succeeded",
        "progress": 100,
        "output":   `{"result_url":"https://..."}`,
    }
    data, _ := json.Marshal(body)
    http.Post(callbackURL, "application/json", bytes.NewBuffer(data))
}
