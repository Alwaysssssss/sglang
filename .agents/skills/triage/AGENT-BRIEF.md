# 编写智能体简报

智能体简报是在 GitHub 问题单或 PR 移到 `ready-for-agent` 时发布的结构化评论，是无人值守智能体执行工作的权威规格。原始正文和讨论属于上下文，智能体简报才是契约。

简报说明**智能体应该做什么**，并同时适用于两种入口：对于问题单，是从零构建改动；对于 PR，是*在现有差异上*完成剩余工作，包括完成实现、补齐缺口、处理审查意见。两者遵循相同原则，下方 PR 示例会展示差异。

## 原则

### 持久性优先于精确位置

问题单可能在 `ready-for-agent` 中停留数天或数周，其间代码库会发生变化。编写简报时应确保即使文件被重命名、移动或重构，内容仍然有用。

- **应当**描述接口、类型和行为契约；
- **应当**指出智能体需要查找或修改的具体类型、函数签名或配置形状；
- **不要**引用文件路径，它们会过时；
- **不要**引用行号；
- **不要**假设当前实现结构会保持不变。

### 描述行为，而不是过程

描述系统**应该做什么**，而不是**如何实现**。智能体会重新探索代码库并自行做出实现决策。

- **良好：**“`SkillConfig` 类型应接受类型为 `CronExpression` 的可选 `schedule` 字段。”
- **不良：**“打开 src/types/skill.ts，在第 42 行添加 schedule 字段。”
- **良好：**“用户不带参数运行 `/triage` 时，应看到需要关注的问题单摘要。”
- **不良：**“在主处理函数中添加 switch 语句。”

### 完整验收标准

智能体需要知道何时完成。每份简报都必须包含具体、可测试的验收标准，并且每项标准都能独立验证。

- **良好：**“运行 `gh issue list --label needs-triage` 会返回已经完成初始分类的问题单。”
- **不良：**“分诊应正常工作。”

### 明确范围边界

写明不在范围内的内容，防止智能体过度润色或对相邻功能做出假设。

## 模板

```markdown
## 智能体简报

**类别：**bug / enhancement
**摘要：**用一行说明需要完成什么

**当前行为：**
描述现在发生什么。对于缺陷，这是损坏行为；
对于增强，这是功能所依赖的现状。

**期望行为：**
描述智能体完成工作后应发生什么。
具体说明边界情况和错误条件。

**关键接口：**
- `TypeName` —— 需要改变什么以及原因
- `functionName()` 返回类型 —— 当前返回什么与应返回什么
- 配置形状 —— 所需的任何新配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**范围之外：**
- 本问题单不应修改或处理的内容
- 看似相关但应单独处理的相邻功能
```

## 示例

### 良好智能体简报（缺陷）

```markdown
## 智能体简报

**类别：**bug
**摘要：**技能描述在单词中间被截断，产生破损输出

**当前行为：**
技能描述超过 1024 个字符时，会严格在第 1024 个字符处截断，
不考虑词语边界，导致描述在词语中间结束，例如“用于用户希望配”。

**期望行为：**
截断应发生在 1024 个字符之前的最后一个词语边界，
并追加“...”表示内容已截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段 —— 无需改变类型，
  但填充该字段的验证或处理逻辑必须尊重词语边界
- 读取 SKILL.md frontmatter 并提取描述的所有函数

**验收标准：**
- [ ] 少于 1024 个字符的描述保持不变
- [ ] 超过 1024 个字符的描述在此前最后一个词语边界处截断
- [ ] 截断后的描述以“...”结尾
- [ ] 包含“...”在内的总长度不超过 1024 个字符

**范围之外：**
- 修改 1024 个字符的限制本身
- 支持多行描述
```

### 良好智能体简报（增强）

```markdown
## 智能体简报

**类别：**enhancement
**摘要：**支持使用 `.out-of-scope/` 目录跟踪被拒绝的功能请求

**当前行为：**
功能请求被拒绝时，问题单会带 `wontfix` 标签和评论关闭。
决策和理由没有持久记录。以后出现相似请求时，
维护者必须凭记忆回想或搜索之前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
包含决策、理由及所有请求该功能的问题单链接。
分诊新问题单时，应检查这些文件是否匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式 —— 每个文件应包含
  `# 概念名称` 标题、`**决策：**` 行、`**理由：**` 行，
  以及带问题单链接的 `**之前的请求：**` 列表
- 分诊工作流应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似度与传入问题单匹配

**验收标准：**
- [ ] 将功能以 wontfix 关闭时，会在 `.out-of-scope/` 中创建或更新文件
- [ ] 文件包含决策、理由及已关闭问题单的链接
- [ ] 已存在匹配的 `.out-of-scope/` 文件时，将新问题单追加到
      “之前的请求”列表，而不是创建重复文件
- [ ] 分诊期间会检查现有 `.out-of-scope/` 文件，并在新问题单
      匹配之前的拒绝时展示

**范围之外：**
- 自动匹配，由人工确认匹配
- 重新打开之前被拒绝的功能
- 缺陷报告，只有被拒绝的增强请求进入 `.out-of-scope/`
```

### 良好智能体简报（PR）

对于 PR，“当前行为”描述差异状态，简报要求智能体完成或修复现有代码，而不是从零构建。

```markdown
## 智能体简报

**类别：**enhancement
**摘要：**完成贡献者为 `triage list` 添加的 `--json` 输出标志

**当前行为：**
PR 添加了 `--json` 标志，将问题单列表序列化为 JSON。正常路径已经工作，
差异符合项目命令结构。仍有两个缺口：错误仍以人类可读文本输出，而不是 JSON；
新标志没有测试覆盖。

**期望行为：**
使用 `--json` 时，包括错误在内的所有标准输出都是格式正确的 JSON，
且命令退出码保持不变。未提供该标志时，现有的人类可读输出保持不变。

**关键接口：**
- 使用 `--json` 时，命令错误路径应输出 `{ "error": string }`，
  而不是纯文本错误
- 复用 PR 已添加的序列化器，不要引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功和错误情况下都输出有效 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 测试覆盖 `--json` 成功输出和一个错误场景
- [ ] 默认的非 JSON 输出逐字节保持不变

**范围之外：**
- 为其他命令添加 `--json`
- 改变 PR 已定义的成功载荷 JSON 形状
```

### 不良智能体简报

```markdown
## 智能体简报

**摘要：**修复分诊缺陷

**需要做什么：**
分诊功能坏了。查看主文件并修复。
第 150 行附近的函数存在问题。

**需要修改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这份简报不良，因为：

- 没有类别；
- 描述模糊，例如“分诊功能坏了”；
- 引用了会过时的文件路径和行号；
- 没有验收标准；
- 没有范围边界；
- 没有描述当前行为与期望行为。
