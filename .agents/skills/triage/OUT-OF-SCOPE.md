# 范围外知识库

仓库中的 `.out-of-scope/` 目录持久记录被拒绝的功能请求，具有两个用途：

1. **组织记忆** —— 记录拒绝功能的原因，使问题单关闭后理由不会丢失；
2. **去重** —— 新问题单与之前的拒绝匹配时，技能能够展示既有决策，而不是重新争论。

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个问题单一个文件。请求同一内容的多个问题单归入同一文件。

## 文件格式

文件应采用轻松、易读的风格，更像简短设计文档，而不是结构化记录条目。使用段落、代码示例和具体例子，使第一次接触的人也能清楚理解理由。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题设置。

## 为什么不在范围内

渲染流程假设只使用 `ThemeConfig` 中定义的一套调色板。
支持多个主题将需要：

- 包裹整个组件树的主题上下文提供者；
- 每个组件都能感知主题的样式解析；
- 用户主题偏好的持久化机制。

这是一项重大的架构变化，与项目专注内容创作的方向不一致。
主题设置应由嵌入或重新分发输出的下游消费者负责。

```ts
// 当前 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 之前的请求

- #42 —— “添加深色模式支持”
- #87 —— “用于无障碍访问的夜间主题”
- #134 —— “深色主题选项”
```

### 文件命名

为概念使用简短、描述性的 kebab-case 名称，例如 `dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够清晰，使浏览目录的人无需打开文件就能理解拒绝了什么。

### 编写理由

理由应具有实质内容，不只写“我们不想要”，而要解释原因。良好理由会引用：

- 项目范围或理念，例如“本项目专注 X，主题设置属于下游职责”；
- 技术约束，例如“支持该功能需要 Y，与当前 Z 架构冲突”；
- 战略决策，例如“我们选择 A 而不是 B，因为……”。

理由应持久有效。避免引用“我们现在太忙”等临时情况；这不是真正拒绝，只是延期。

## 何时检查 `.out-of-scope/`

分诊期间，在第 1 步“收集上下文”中读取 `.out-of-scope/` 的所有文件。评估新问题单时：

- 检查请求是否与现有范围外概念匹配；
- 按概念相似度而不是关键词匹配，例如“夜间主题”与 `dark-mode.md` 匹配；
- 找到匹配时向维护者展示：“这与 `.out-of-scope/dark-mode.md` 相似；之前因为[原因]拒绝。现在仍保持相同决定吗？”

维护者可以：

- **确认** —— 将新问题单加入现有文件的“之前的请求”列表，然后关闭；
- **重新考虑** —— 删除或更新范围外文件，问题单继续正常分诊；
- **不同意匹配** —— 两个问题相关但不同，继续正常分诊。

## 何时写入 `.out-of-scope/`

只有**增强请求**而非缺陷被*拒绝*为 `wontfix` 时才写入。这同样适用于增强 PR 和问题单；被拒绝的 PR 记录在此，避免相同请求以后以新代码形式再次出现。

因**已经实现**而以 `wontfix` 关闭时，不要写入这里。它是已构建功能，而不是被拒绝功能；记录后会用虚假拒绝污染去重检查。关闭评论应改为指向功能现有位置。

流程：

1. 维护者决定功能请求不在范围内；
2. 检查是否已有匹配的 `.out-of-scope/` 文件；
3. 如果有，将新问题单追加到“之前的请求”列表；
4. 如果没有，创建新文件，包含概念名称、决策、理由和第一项之前请求；
5. 在问题单发布评论，解释决策并提及 `.out-of-scope/` 文件；
6. 使用 `wontfix` 标签关闭问题单。

## 更新或删除范围外文件

维护者改变对之前被拒绝概念的决定时：

- 删除 `.out-of-scope/` 文件；
- 无需重新打开旧问题单，它们属于历史记录；
- 触发重新考虑的新问题单继续正常分诊。
