# 问题分诊

推动项目问题跟踪器中的问题单经过一个小型分诊角色状态机。

如果当前仓库把外部拉取请求作为请求入口，参见问题跟踪器配置，则分诊也覆盖它们：**PR 是附带代码的问题单**。它使用相同角色、状态和状态机，少量差异会在下文标为“对于 PR”。按跟踪器配置将单独的 `#42` 解析为问题单或 PR。

分诊期间发布到问题跟踪器的每条评论或问题单都**必须**以以下免责声明开头：

```
> *此内容由 AI 在问题分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) —— 如何编写持久有效的智能体简报；
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) —— `.out-of-scope/` 知识库的工作方式。

## 角色

两种**类别**角色：

- `bug` —— 某项功能损坏；
- `enhancement` —— 新功能或改进。

五种**状态**角色：

- `needs-triage` —— 需要维护者评估；
- `needs-info` —— 等待报告者提供更多信息；
- `ready-for-agent` —— 规格完整，可供无人值守智能体处理；
- `ready-for-human` —— 需要人工实现；
- `wontfix` —— 不会处理。

对于 PR，应结合附带代码理解相同状态：`ready-for-agent` 表示已经附上简报，智能体应继续处理差异；`ready-for-human` 表示已可由人工合并。

每个已分诊问题单必须恰好拥有一个类别角色和一个状态角色。状态角色冲突时，先标记并询问维护者，不要执行其他操作。

这些是规范角色名，问题跟踪器实际使用的标签字符串可能不同。应当已经提供映射；如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：无标签问题单通常先进入 `needs-triage`，再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖；看起来异常的转换应先标记并询问，再继续。

## 调用方式

维护者调用 `/triage` 并用自然语言描述需求。解释请求并执行，例如：

- “显示需要我关注的内容”
- “查看 #42”（问题单或 PR）
- “把 #42 移到 ready-for-agent”
- “哪些内容已经可供智能体领取？”

## 展示需要关注的内容

查询问题跟踪器，按最旧优先展示三组：

1. **无标签** —— 从未分诊；
2. **`needs-triage`** —— 正在评估；
3. **自上次分诊记录后报告者有新活动的 `needs-info`** —— 需要重新评估。

PR 在范围内时，将外部 PR 加入这些分组，并为每行标记 `[PR]` 或 `[问题单]`。发现流程只展示*外部* PR，何谓外部由跟踪器配置定义；协作者进行中的 PR 不属于分诊工作。该过滤器只用于发现；明确指定的 PR 无论作者是谁都要分诊。

显示数量和每项的一行摘要，让维护者选择。

## 分诊指定问题单或 PR

1. **收集上下文。**读取完整问题单或 PR，包括正文、评论、标签、作者和日期；对于 PR 还要读取差异。解析之前的分诊记录，避免重复询问已经解决的问题。使用项目领域术语表探索代码库，并遵守所涉区域的 ADR。对代码库执行两项检查：(a) **冗余** —— 按领域概念而不只按请求措辞搜索所需行为的现有实现，并报告搜索位置。找到时，结果是“已经实现”的 `wontfix`，参见第 5 步；(b) **之前拒绝** —— 读取 `.out-of-scope/*.md`，展示与当前请求相似的内容。

2. **提出建议。**向维护者说明建议的类别和状态及其理由，并提供与请求相关的简短代码库摘要，包括是否已经实现。等待指示。

3. **验证主张。**深入追问之前先检查主张是否成立。对于缺陷，按报告者步骤复现；对于 PR，检出并运行相关测试或命令，确认差异符合其主张。报告结果：已确认（附代码路径）、验证失败，或细节不足（强烈表明应进入 `needs-info`）。经过确认的验证能形成更有力的智能体简报。

4. **深入追问（如需要）。**请求需要充实时，同时运行 `/grilling` 和 `/domain-modeling` 技能，一次提出一个问题，收紧领域术语，并在决策形成时就地更新 `CONTEXT.md` 和 ADR。

5. **应用结果：**
   - `ready-for-agent` —— 发布智能体简报评论，参见 [AGENT-BRIEF.md](AGENT-BRIEF.md)；
   - `ready-for-human` —— 使用与智能体简报相同的结构，但说明无法委派的原因，例如判断项、外部访问、设计决策或手动测试；
   - `needs-info` —— 发布分诊记录，模板见下方；
   - `wontfix` —— 关闭问题单，并根据*原因*选择评论：
     - **已经实现** —— 改动已经存在于代码库中。指出所在位置；不要写入 `.out-of-scope/`，该知识库用于*被拒绝*的请求，而不是已构建功能；
     - **拒绝（缺陷）** —— 礼貌解释后关闭；
     - **拒绝（增强）** —— 写入 `.out-of-scope/`，在评论中链接该文件，再关闭，参见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)；
   - `needs-triage` —— 应用该角色。已有部分进展时可选发布评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，应信任并直接应用该角色。确认即将执行的操作，包括角色变化、评论和关闭，再采取行动。跳过深入追问。未经过追问就移到 `ready-for-agent` 时，询问是否需要编写智能体简报。

## 信息不足模板

```markdown
## 分诊记录

**目前已经确认：**

- 要点 1
- 要点 2

**仍需要你提供（@reporter）：**

- 问题 1
- 问题 2
```

将深入追问期间解决的所有内容记录在“目前已经确认”下，避免成果丢失。问题必须具体且可操作，不能只写“请提供更多信息”。

## 恢复之前的会话

问题单或 PR 中存在之前的分诊记录时，先读取并检查报告者是否回答了待解决问题，再展示更新后的情况并继续。不要重复询问已经解决的问题。
