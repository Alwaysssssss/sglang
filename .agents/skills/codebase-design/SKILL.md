# 代码库设计

设计**深模块**：在干净接缝处，用小接口隐藏大量行为，并可通过该接口测试。设计或重构代码时统一使用这套语言和原则，目标是为调用方提供杠杆率，为维护者提供局部性，并让所有人都能轻松测试。

## 术语表

严格使用以下术语，不要用“组件”“服务”“API”或“边界”替代。统一语言正是本词汇体系的目的。

**模块** —— 任何同时拥有接口和实现的事物。刻意不限定规模，可以是函数、类、包或跨层切片。_避免使用_：单元、组件、服务。

**接口** —— 调用方正确使用模块必须了解的全部内容：不仅包括类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、签名，因为它们过于狭窄，只表示类型层表面。

**实现** —— 模块内部的代码主体。它与**适配器**不同：一个事物可以是小型适配器但拥有大型实现，例如 Postgres 仓储；也可以是大型适配器但拥有小型实现，例如内存替身。讨论接缝时使用“适配器”，其他情况使用“实现”。

**深度** —— 接口提供的杠杆率：调用方或测试每学习一单位接口，能够驱动多少行为。小接口背后包含大量行为时，模块是**深的**；接口几乎与实现一样复杂时，模块是**浅的**。

**接缝**（Michael Feathers）—— 无需在该位置编辑代码即可改变行为的地方，也是模块接口所在的*位置*。接缝放在哪里是一项独立设计决策，与其背后放置什么不同。_避免使用_：边界，因为它与 DDD 的限界上下文含义重叠。

**适配器** —— 在接缝处满足某个接口的具体事物。它描述的是*角色*，即填补哪个插槽，而不是内部实质。

**杠杆率** —— 调用方从深度中获得的收益：每学习一单位接口即可获得更多能力。一次实现可在 N 个调用点和 M 个测试中产生回报。

**局部性** —— 维护者从深度中获得的收益：改动、缺陷、知识和验证集中在一个位置，而不散布到各调用方。修复一次，处处生效。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口         │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│       深实现         │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 只做透传
└─────────────────────────────────┘
```

设计接口时，询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，不是实现的属性。**深模块内部可以由小型、可模拟、可替换的部件组成，只是这些部件不属于接口。模块既可以拥有实现私有、供自身测试使用的**内部接缝**，也可以在接口处拥有**外部接缝**。
- **删除测试。**想象删除该模块。如果复杂性随之消失，它只是透传层；如果复杂性重新出现在 N 个调用方中，它就发挥了价值。
- **接口就是测试表面。**调用方和测试跨越同一接缝。如果希望越过接口测试内部，模块的形状可能不正确。
- **一个适配器意味着假想接缝，两个适配器意味着真实接缝。**只有确实存在跨接缝变化的事物时才引入接缝。

## 为可测试性而设计

良好接口让测试自然发生：

1. **接收依赖，不要创建依赖。**

   ```typescript
   // 易于测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要制造副作用。**

   ```typescript
   // 易于测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **保持较小表面积。**方法越少，需要的测试越少；参数越少，测试设置越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**，即向调用方和测试呈现的表面。
- **深度**是**模块**的属性，以其**接口**为参照进行衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用方带来**杠杆率**，为维护者带来**局部性**。

## 不采用的表述

- **把深度定义为实现代码行数与接口代码行数之比**（Ousterhout）：这种定义会奖励膨胀实现。这里改用“深度即杠杆率”。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：过于狭窄。这里的接口包括调用方必须了解的每项事实。
- **“边界”**：与 DDD 的限界上下文含义重叠。应使用**接缝**或**接口**。
