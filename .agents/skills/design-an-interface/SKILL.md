# 设计接口

本技能基于《软件设计的哲学》中的“设计两次”：第一个想法通常不会是最佳方案。先生成多个截然不同的设计，再进行比较。

## 工作流

### 1. 收集需求

设计前先明确：

- [ ] 这个模块解决什么问题？
- [ ] 调用方是谁？（其他模块、外部用户、测试）
- [ ] 关键操作有哪些？
- [ ] 存在哪些约束？（性能、现有模式）
- [ ] 哪些内容应隐藏在内部，哪些应暴露？

询问：“这个模块需要做什么？谁会使用它？”

### 2. 生成设计（并行子智能体）

使用 Task 工具同时启动至少 3 个子智能体。每个子智能体都必须产出一种**截然不同**的方案。

```
每个子智能体的提示词模板：

为以下对象设计接口：[模块描述]

需求：[已收集的需求]

本设计的约束：[为每个智能体分配不同约束]
- 智能体 1：“尽量减少方法数量，最多使用 1–3 个方法”
- 智能体 2：“尽量提高灵活性，支持多种用例”
- 智能体 3：“针对最常见用例优化”
- 智能体 4：“借鉴[特定范式或库]”

输出格式：
1. 接口签名（类型或方法）
2. 使用示例（调用方如何使用）
3. 本设计在内部隐藏了什么
4. 本方案的取舍
```

### 3. 展示设计

展示每种设计的以下内容：

1. **接口签名**——类型、方法、参数
2. **使用示例**——调用方在实践中如何使用
3. **隐藏内容**——保留在内部的复杂度

依次展示设计，使用户能先理解每种方案，再进行比较。

### 4. 比较设计

展示全部设计后，从以下维度比较：

- **接口简洁性**：方法更少、参数更简单
- **通用与专用**：灵活性与聚焦程度
- **实现效率**：接口形态是否允许高效的内部实现？
- **深度**：小接口隐藏显著复杂度（好）与大接口搭配单薄实现（差）
- **正确使用的难易度**与**误用的难易度**

使用文字讨论取舍，不要使用表格。突出各设计分歧最大的地方。

### 5. 综合方案

最佳设计往往会结合多个方案的洞见。询问：

- “哪种设计最符合你的主要用例？”
- “其他设计中是否有值得吸收的元素？”

## 评估标准

以下标准来自《软件设计的哲学》：

**接口简洁性**：方法越少、参数越简单，就越容易学习并正确使用。

**通用性**：无需改动即可处理未来用例，但要警惕过度泛化。

**实现效率**：接口形态是允许高效实现，还是迫使内部设计变得别扭？

**深度**：小接口隐藏大量复杂度就是深模块（好）；大接口只有单薄实现就是浅模块（应避免）。

## 反模式

- 不要让子智能体产出相似设计——必须保证方案截然不同
- 不要跳过比较——价值来自对照
- 不要实现——本技能只讨论接口形态
- 不要根据实现工作量评估方案
