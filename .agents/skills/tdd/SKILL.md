# 测试驱动开发

TDD 是红 → 绿循环。本技能说明如何让该循环产出值得保留的测试：良好测试的定义、测试位置、反模式和循环规则。每个章节都适用于每次循环，应在循环之前和期间查阅，而不是事后。

探索代码库时，读取 `CONTEXT.md`（如存在），使测试名称和接口词汇符合项目领域语言，并遵守所涉区域的 ADR。

## 什么是良好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变，测试不应随之改变。良好测试读起来像规格，例如“用户可以使用有效购物车结算”准确说明已有能力，并且由于不关心内部结构，能够经受重构。

示例参见 [tests.md](tests.md)，模拟指南参见 [mocking.md](mocking.md)。

## 接缝：测试应放在哪里

**接缝**是执行测试的公共位置：无需进入内部即可观察行为的接口。测试位于接缝处，绝不针对内部实现。

**只在预先约定的接缝处测试。**编写任何测试前，写下要测试的接缝并与用户确认。不得在未确认的接缝处编写测试。无法测试一切；预先约定接缝可让测试精力落在关键路径和复杂逻辑上，而不是每个边界情况。

询问：“公共接口是什么？我们应测试哪些接缝？”

## 反模式

- **与实现耦合** —— 模拟内部协作者、测试私有方法，或通过旁路而不是接口验证。判断信号是：行为没有改变，测试却因重构而失败。
- **同义反复** —— 断言以与代码相同的方式重新计算期望值，例如 `expect(add(a, b)).toBe(a + b)`、用相同方式手工推导快照，或断言常量等于自身，因此测试从构造上必然通过，永远无法与代码产生分歧。期望值必须来自独立事实源，例如已知正确字面值、完整算例或规格。
- **水平切片** —— 先编写全部测试，再实现全部代码。批量测试验证的是*想象中的*行为：测试事物的*形状*而非用户可见行为，对真实改动不敏感，并在理解实现前就锁定测试结构。应使用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是响应上一循环所学内容的**曳光弹**。

## 循环规则

- **先红后绿。**先编写失败测试，再只写足以通过测试的代码。不要预判未来测试，也不要添加推测性功能。
- **每次一个切片。**每个循环只包含一个接缝、一个测试和一个最小实现。
- **重构不属于循环。**重构属于审查阶段，参见 `code-review` 技能，而不是红 → 绿实现循环。
