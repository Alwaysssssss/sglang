# 质量验证会话

运行交互式质量验证会话。用户描述遇到的问题；你负责澄清、探索代码库以获取上下文，并创建持久有效、聚焦用户且使用项目领域语言的 GitHub 议题。

## 针对用户提出的每个问题

### 1. 倾听并适度澄清

让用户用自己的话描述问题。最多提出 **2–3 个简短的澄清问题**，重点关注：

- 预期发生什么，实际发生什么
- 复现步骤（如果并不明显）
- 问题是稳定出现还是间歇出现

**不要**过度访谈。如果描述已足够创建议题，直接继续。

### 2. 在后台探索代码库

与用户交谈的同时，在后台启动一个智能体（`subagent_type=Explore`）了解相关区域。目标**不是**找到修复方案，而是：

- 了解该区域使用的领域语言（检查 `UBIQUITOUS_LANGUAGE.md`）
- 理解功能原本应该做什么
- 确定面向用户的行为边界

这些上下文有助于写出更好的议题，但议题本身**不应**引用具体文件、行号或内部实现细节。

### 3. 评估范围：单一议题还是拆分？

创建之前，判断这是一个**单一议题**，还是需要**拆分**成多个议题。

在以下情形拆分：

- 修复横跨多个独立区域（例如“表单校验错误、成功消息缺失、重定向也失效”）
- 存在明显可分离的关注点，可由不同人员并行处理
- 用户描述的事项包含多个不同的失败模式或症状

在以下情形保留为单一议题：

- 只有一个位置的一项行为出错
- 所有症状都由同一个根本行为引起

### 4. 创建 GitHub 议题

使用 `gh issue create` 创建议题。**不要**先让用户审阅，直接创建并分享 URL。

议题必须**持久有效**——即使经过大型重构，仍应表意清晰。使用用户视角编写。

#### 单一议题

使用以下模板：

```
## 实际发生了什么

[用直白语言描述用户实际遇到的行为]

## 我的预期

[描述预期行为]

## 复现步骤

1. [开发者可以照做的具体编号步骤]
2. [使用代码库中的领域术语，不使用内部模块名]
3. [包含相关输入、标志或配置]

## 补充背景

[用户提供或代码库探索所得、能够帮助界定问题的其他观察，例如“只在使用 Docker 层时发生，使用文件系统层时不会”——使用领域语言，但不要引用文件]
```

#### 拆分为多个议题

按依赖顺序创建议题（阻塞项优先），从而可以引用真实议题编号。

每个子议题使用以下模板：

```
## 父议题

#<父议题编号>（如果创建了跟踪议题），或“在质量验证会话中报告”

## 存在什么问题

[描述这一项具体行为问题——只描述当前切片，不要重复完整报告]

## 我的预期

[这一具体切片的预期行为]

## 复现步骤

1. [只针对当前议题的步骤]

## 阻塞项

- #<议题编号>（如果必须先解决另一个议题才能修复当前议题）

没有阻塞项时填写“无——可以立即开始”。

## 补充背景

[与当前切片相关的其他观察]
```

拆分议题时：

- **宁可创建多个小议题，也不要创建少数庞大议题**——每个议题都应能独立修复和验证
- **如实标记阻塞关系**——如果议题 B 确实必须等议题 A 修复后才能测试，就明确说明。如果彼此独立，两者都标记“无——可以立即开始”
- **按依赖顺序创建议题**，以便在“阻塞项”中引用真实议题编号
- **最大化并行度**——目标是让多个人或智能体能够同时领取不同议题

#### 所有议题正文的规则

- **不要包含文件路径或行号**——它们会过时
- **使用项目的领域语言**（如果存在 `UBIQUITOUS_LANGUAGE.md`，请检查）
- **描述行为，而不是代码**——写“同步服务无法应用补丁”，不要写“`applyPatch()` 在第 42 行抛出异常”
- **必须提供复现步骤**——无法确定时询问用户
- **保持简洁**——开发者应能在 30 秒内读完议题

创建后，打印所有议题 URL（同时总结阻塞关系），并询问：“继续下一个问题，还是已经完成？”

### 5. 继续会话

持续进行，直到用户表示结束。每个议题相互独立，不要批量处理。
