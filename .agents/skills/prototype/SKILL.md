# 原型验证

原型是**用于回答一个问题的一次性代码**。问题决定其形状。

## 选择分支

根据用户提示、周边代码，或在用户在线时询问，确定要回答的问题：

- **“这个逻辑或状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个小型交互式终端应用，让状态机运行经过难以在纸面上推理的场景。
- **“它应该是什么样子？”** → [UI.md](UI.md)。在单一路由上生成几个截然不同的界面变体，并通过 URL 查询参数和底部悬浮栏切换。

两个分支产生完全不同的产物，选错会浪费整个原型。如果问题确实含糊且无法联系用户，默认选择更符合周边代码的分支：后端模块选择逻辑，页面或组件选择界面，并在原型顶部写明假设。

## 两个分支的共同规则

1. **从第一天起就是一次性代码，并明确标记。**将原型代码放在未来实际使用位置附近，例如紧邻目标模块或页面，使上下文清晰；同时通过命名让普通读者能看出它是原型而非生产代码。一次性界面路由应遵循项目现有路由惯例，不要发明新的顶层结构。
2. **只需一条运行命令。**使用项目现有任务运行器支持的形式，例如 `pnpm <name>`、`python <path>`、`bun <path>`。用户应无需思考即可启动。
3. **默认不持久化。**状态只存在于内存。持久化应是原型要*验证*的内容，而不是其依赖。问题明确涉及持久化时，使用一次性本地存储或本地文件，并使用清晰的“原型——可清除”名称。
4. **跳过润色。**不写测试，不添加超出“使原型可运行”所需的错误处理，也不做抽象。目标是快速获得结论。
5. **暴露状态。**每次操作（逻辑）或切换变体（界面）后，打印或渲染完整相关状态，让用户看见变化。
6. **完成后保留证据。**将验证通过的决策吸收到真实代码中，再把原型本身作为**一手来源**保存：提交到主分支之外的一次性分支，并在实现问题单中留下指向该分支的上下文指针。同时在问题单或提交中记录答案，即结论及其解决的问题。主分支只保留已验证决策。
