# 界面原型

在单一路由上生成**几个截然不同的界面变体**，通过底部悬浮栏切换。用户在浏览器中比较变体，选择一个或组合各自优点，再丢弃其余方案。

如果问题关注逻辑或状态，而不是外观，说明选错了分支，应使用 [LOGIC.md](LOGIC.md)。

## 适用场景

- “这个页面应该是什么样子？”
- “决定之前，我想看看这个仪表盘的几个方案。”
- “为设置页面尝试不同布局。”
- 用户可能花一整天在脑中比较三个模糊模型的任何情况。

## 两种子形态：强烈优先选择 A

界面原型与应用其余部分**紧密相邻**时更容易判断，因为此时有真实页头、侧栏、数据和信息密度。独立的一次性路由处于真空中，每个变体单独看都不错。只要存在能够承载变体的合理现有页面，就默认选择子形态 A；原型确实没有邻近归属时才选择 B。

### 子形态 A：调整现有页面（首选）

路由已经存在。通过 `?variant=` URL 查询参数在**同一路由**上渲染不同变体。保留现有数据获取、参数和身份验证，只替换渲染内容。除非有明确理由，否则默认选择此形态。

如果原型尚无独立页面，但*自然属于某个页面内部*，例如仪表盘的新区域、设置页面的新卡片、现有流程的新步骤，仍属于子形态 A。将变体挂载到宿主页面内部。

### 子形态 B：新页面（最后手段）

只有原型确实无法放入任何现有页面时才使用，例如全新的顶层界面，或无法合理嵌入其他位置的流程。

按项目现有路由惯例创建**一次性路由**，不要发明新的顶层结构。通过命名明确表明它是原型，例如在路径或文件名中加入 `prototype`。同样使用 `?variant=` 模式。

选择子形态 B 前先做合理性检查：真的没有可嵌入的现有页面吗？空路由会隐藏在真实内容页面中才会暴露的设计问题。

两种子形态使用相同的底部悬浮栏。

## 流程

### 1. 写明问题并确定数量

默认生成 **3 个变体**。超过 5 个后，方案不再截然不同，反而开始形成噪声，因此最多 5 个。

在原型所在位置或文件顶部注释中，用一行写下计划：

> “在现有 `/settings` 路由上创建三个设置页面变体，通过 `?variant=` 切换。”

无论用户是否在线提出异议，这一做法都适用。

### 2. 生成截然不同的变体

为每个变体起草方案，并确保符合：

- 页面用途及其可访问的数据；
- 项目的组件库或样式系统，例如 TailwindCSS、shadcn、MUI、原生 CSS；
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**，包括不同布局、信息层级和主要操作方式，而不只是颜色不同。三个略有调整的卡片网格不是界面原型，只是壁纸。如果两个草案过于相似，明确要求“不要使用卡片网格”并重做其中一个。

### 3. 连接变体

在路由上创建一个统一切换器组件：

```tsx
// 伪代码：按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面），将全部现有数据获取逻辑保留在切换器上方，只让渲染子树随变体变化。

对于子形态 B（新页面），在 `/prototype/<name>` 下的一次性路由中挂载相同切换器。

### 4. 构建悬浮切换器

在屏幕底部中央放置一个小型固定定位栏，包含三部分：

- **左箭头** —— 循环切换到上一个变体；
- **变体标签** —— 显示当前变体键；如果变体导出名称，也一并显示，例如 `B — 侧栏布局`；
- **右箭头** —— 循环切换到下一个变体。

行为：

- 单击箭头时更新 URL 查询参数。使用框架路由，例如 Next 的 `router.replace`、React Router 的 `navigate`，使变体可分享且重新加载后保持稳定。
- 键盘 `←` 和 `→` 也可循环切换。当焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时，不拦截方向键。
- 视觉上与页面明显区分，例如使用高对比胶囊和轻微阴影，使其显然不属于被评估的设计。
- 在生产构建中隐藏。使用 `process.env.NODE_ENV !== 'production'` 或等效检查，避免意外合并原型后把切换栏交付给用户。

将切换器放入单个共享组件，使两种子形态能够复用，并遵循项目共享界面的现有位置。

### 5. 交给用户

提供 URL 和 `?variant=` 键。用户可以在方便时逐个查看。最有价值的反馈通常是**“我想要 B 的页头和 C 的侧栏”**，这才是用户真正需要的设计。

### 6. 记录答案并清理

选出获胜变体后，记录答案，包括选择哪个以及原因，再按 [SKILL](SKILL.md) 的说明保存原型。将获胜方案吸收到真实代码，把其余内容移到一次性分支，而不是主分支：

- **子形态 A** —— 将获胜方案吸收到现有页面，从主分支删除落选变体和切换器；
- **子形态 B** —— 将获胜变体提升为真实路由，从主分支删除一次性路由和切换器。

完整变体集属于一手来源，应保存在一次性分支，而不是直接丢弃。变体组件和切换器若留在主分支，会迅速腐化并使下一位读者困惑。

## 反模式

- **变体只在颜色或文案上不同。**这只是微调，不是原型。真正的变体在结构上存在分歧。
- **变体之间共享过多代码。**共享 `<Header>` 没问题，共享 `<Layout>` 则违背目的。每个变体都应能自由抛弃现有布局。
- **把变体连接到真实写操作。**只读原型没有问题。需要写操作时连接到桩；要回答的问题是“它应该是什么样子”，而不是“后端是否工作”。
- **把原型直接提升到生产环境。**变体代码是在原型约束下编写的，没有测试且错误处理最少。吸收到正式实现时应正确重写。
