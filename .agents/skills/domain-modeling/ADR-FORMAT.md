# ADR 格式

ADR 位于 `docs/adr/`，并使用连续编号，例如 `0001-slug.md`、`0002-slug.md`。

按需创建 `docs/adr/` 目录，只在需要第一份 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{用 1–3 句话说明背景、所做决策及其原因。}
```

到此即可。ADR 可以只有一个段落，其价值在于记录*做出了什么决策*以及*为什么*，而不是填满章节。

## 可选章节

只有确实增加价值时才包含以下内容，大多数 ADR 都不需要：

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 重新审视决策时有用；
- **考虑过的方案** —— 只有被拒绝的备选方案值得记住时才加入；
- **后果** —— 只有需要明确指出不明显的下游影响时才加入。

## 编号

扫描 `docs/adr/` 中现有的最大编号并加一。

## 何时建议 ADR

必须同时满足以下三个条件：

1. **难以撤销** —— 日后改变决定的成本显著；
2. **缺少上下文时令人意外** —— 未来读者看到代码会疑惑“为什么要这样做？”；
3. **真实取舍的结果** —— 确实存在备选方案，并因具体理由选择其中之一。

容易撤销的决策无需记录，因为届时直接撤销即可。并不意外的决策不会让人追问原因。不存在真实备选方案时，除了“采用了显而易见的做法”也没有值得记录的内容。

### 符合条件的内容

- **架构形状。**例如“采用单体仓库”“写模型使用事件溯源，读模型投影到 Postgres”。
- **上下文之间的集成模式。**例如“订单与计费通过领域事件通信，而不是同步 HTTP”。
- **带来锁定效应的技术选择。**例如消息总线、身份验证提供商、部署目标等。并非每个库都值得记录，只记录需要数月才能替换的选择。
- **边界和范围决策。**例如“客户数据归客户上下文所有，其他上下文只通过 ID 引用”。明确的否定与肯定同样有价值。
- **有意偏离显而易见路径的决策。**例如“因为 X 使用手写查询而不是 ORM”。合理读者可能默认相反做法的内容都应记录，以免下一位工程师错误地“修复”一项有意决策。
- **代码中不可见的约束。**例如“合规要求禁止使用 AWS”“合作方 API 合同要求响应时间低于 200 毫秒”。
- **拒绝理由不明显的备选方案。**如果曾考虑 GraphQL，却因细微原因选择 REST，应将其记录，否则六个月后还会有人再次建议 GraphQL。
