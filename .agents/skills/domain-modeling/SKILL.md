# 领域建模

在设计过程中主动构建并完善项目的领域模型。这是一项*主动*纪律：质疑术语、构造边界场景，并在术语和决策形成的当下写入文档。仅仅*读取* `CONTEXT.md` 获取词汇不属于本技能，那是任何技能都能做到的一行习惯。本技能用于改变模型，而不只是使用模型。

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库包含多个上下文。该映射指出每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件，只在确有内容可写时创建。没有 `CONTEXT.md` 时，在第一个术语得到解决后创建；没有 `docs/adr/` 时，在需要第一份 ADR 时创建。

## 会话期间

### 对照术语表质疑

用户使用的术语与 `CONTEXT.md` 现有语言冲突时，立即指出：“术语表将‘取消’定义为 X，但你现在似乎表示 Y。应以哪个为准？”

### 收紧模糊语言

用户使用含糊或一词多义的术语时，提出精确的规范术语：“你所说的‘账户’是指客户还是用户？它们是两个不同概念。”

### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。构造能够探查边界情况的场景，促使用户精确说明概念之间的边界。

### 与代码交叉核对

用户说明某项行为时，检查代码是否一致。如果发现矛盾，明确指出：“代码会取消整个订单，但你刚才说可以部分取消。哪一种才正确？”

### 就地更新 CONTEXT.md

术语得到解决时立即更新 `CONTEXT.md`，不要批量积攒；结论形成时就将其捕获。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 不得包含任何实现细节。不要把它当作规格、草稿纸或实现决策仓库；它只能是术语表。

### 谨慎建议 ADR

只有同时满足以下三个条件时才建议创建 ADR：

1. **难以撤销** —— 日后改变决定的成本显著；
2. **缺少上下文时令人意外** —— 未来读者会疑惑“为什么这样做？”；
3. **真实取舍的结果** —— 确实存在备选方案，并因具体理由选择其中之一。

任一条件不满足就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
