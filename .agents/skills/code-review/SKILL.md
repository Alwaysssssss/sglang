从两个维度审查 `HEAD` 与用户提供的固定点之间的差异：

- **规范**——代码是否符合仓库记录的编码规范？
- **规格**——代码是否忠实实现了原始议题、PRD 或规格？

两个维度由**并行子智能体**分别运行，避免相互污染上下文，随后由本技能汇总发现。

系统应已提供议题跟踪器配置；如果缺少 `docs/agents/issue-tracker.md`，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户指定的内容就是固定点——提交 SHA、分支名、标签、`main`、`HEAD~5` 等。如果用户未指定，则询问。

一次性确定差异命令：`git diff <固定点>...HEAD`（三点语法，因此以合并基点为比较基准）。同时通过 `git log <固定点>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点能够解析（`git rev-parse <固定点>`），且差异不为空。无效引用或空差异应在此处失败，而不是在两个并行子智能体内部失败。

### 2. 确定规格来源

按以下顺序查找原始规格：

1. 提交消息中的议题引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户通过参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD 或规格文件。
4. 如果仍未找到，询问用户规格位于何处。如果用户表示没有规格，则跳过**规格**子智能体，并报告“没有可用规格”。

### 3. 确定规范来源

查找仓库中所有记录代码编写方式的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库记录的规范外，规范维度始终携带下述**坏味道基线**——一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库没有任何书面规范也适用。它受两条规则约束：

- **仓库规范优先。** 有明确记录的仓库规范始终优先；如果仓库规范认可了基线本会标记的做法，则不报告该坏味道。
- **始终需要判断。** 每种坏味道都是带标签的启发式判断（例如“可能存在依恋情结”），绝不是硬性违规；与这里的任何规范一样，跳过工具已经强制执行的内容。

每种坏味道都按“*它是什么* → *如何修复*”描述；据此检查差异：

- **神秘命名**——函数、变量或类型的名称无法说明其作用或所保存的内容。→ 重命名；如果找不到诚实准确的名称，说明设计仍然含混。
- **重复代码**——同一种逻辑结构出现在改动中的多个差异块或文件里。→ 提取共享结构，并从两处调用。
- **依恋情结**——某个方法访问另一个对象的数据多于访问自身数据。→ 将方法移到它所依恋的数据上。
- **数据泥团**——相同的若干字段或参数总是成组出现（一个等待诞生的类型）。→ 将它们组合成一个类型并整体传递。
- **基本类型偏执**——用基本类型或字符串代表一个理应拥有独立类型的领域概念。→ 为该概念创建小型专用类型。
- **重复条件分支**——针对同一类型的相同 `switch` 或 `if` 级联在改动中反复出现。→ 使用多态替代，或让两处共享同一映射。
- **霰弹式修改**——一项逻辑改动迫使差异分散修改许多文件。→ 将一起变化的内容收拢到同一模块。
- **发散式变化**——同一文件或模块因多个互不相关的原因被修改。→ 拆分模块，使每个模块只因一种原因变化。
- **夸夸其谈的通用性**——为规格并未要求的需求添加抽象、参数或钩子。→ 删除它；不断内联，直到出现真实需求。
- **过长消息链**——调用方依赖本不该了解的长串 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法隐藏这段遍历。
- **中间人**——类或函数主要只负责向下委派。→ 移除它，直接调用真正的目标。
- **被拒绝的遗赠**——子类或实现者忽略或覆盖了继承内容中的大部分。→ 放弃继承，改用组合。

### 4. 并行启动两个子智能体

在同一条消息中发出两次 `Agent` 工具调用。两者都使用 `general-purpose` 子智能体。

**规范子智能体提示词**——包括：

- 完整的差异命令与提交列表。
- 步骤 3 中找到的规范来源文件列表，**以及步骤 3 的完整坏味道基线**——子智能体无法通过其他方式访问它。
- 任务简述：“按相关文件或差异块报告：(a) 差异中每处违反书面规范的位置，并引用规范（文件与规则）；(b) 发现的所有基线坏味道，注明名称并引用差异块。区分硬性违规与判断项——书面规范违规可以是硬性的，但基线坏味道始终只是判断项，且仓库书面规范优先于基线。跳过工具已强制执行的内容。控制在 400 字以内。”

**规格子智能体提示词**——包括：

- 差异命令与提交列表。
- 规格路径或已获取的规格内容。
- 任务简述：“报告：(a) 规格要求但缺失或只完成一部分的内容；(b) 差异中规格未要求的行为（范围蔓延）；(c) 看似已实现但实现方式有误的要求。每项发现都引用对应规格行。控制在 400 字以内。”

如果缺少规格，跳过规格子智能体，并在最终报告中说明。

### 5. 汇总

将两份报告分别放在 `## 规范` 和 `## 规格` 标题下，保持原文或仅做轻微整理。**不要**合并发现或重新排序——两个维度是有意分开的（参见“为什么使用两个维度”）。

最后用一行总结：各维度的发现总数，以及_各自维度内_最严重的问题（如有）。不要跨维度选出单一最严重项——分离维度正是为了避免这种重新排序。

## 为什么使用两个维度

一项改动可能通过一个维度，却在另一个维度失败：

- 代码遵守了所有规范，却实现了错误内容 → **规范通过，规格失败。**
- 代码完全实现了议题要求，却破坏了项目约定 → **规格通过，规范失败。**

分开报告可以防止一个维度掩盖另一个维度。
