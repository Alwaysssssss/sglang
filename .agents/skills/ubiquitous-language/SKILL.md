# 通用语言

从当前对话中提取并规范化领域术语，形成一致的术语表并保存到本地文件。

## 流程

1. **扫描对话**，查找与领域相关的名词、动词和概念
2. **识别问题**：
   - 同一个词用于不同概念（歧义）
   - 不同词用于同一概念（同义词）
   - 含糊或含义过载的术语
3. **提出规范术语表**，明确选择推荐用词
4. 按下述格式**写入工作目录中的 `UBIQUITOUS_LANGUAGE.md`**
5. **在对话中输出摘要**

## 输出格式

按以下结构编写 `UBIQUITOUS_LANGUAGE.md`：

```md
# 通用语言

## 订单生命周期

| 术语       | 定义                                     | 应避免的别名     |
| ---------- | ---------------------------------------- | ---------------- |
| **订单**   | 客户购买一个或多个商品的请求             | 购买、交易       |
| **发票**   | 交付后向客户发出的付款请求               | 账单、付款请求   |

## 参与者

| 术语       | 定义                         | 应避免的别名       |
| ---------- | ---------------------------- | ------------------ |
| **客户**   | 下达订单的个人或组织         | 委托方、买家、账户 |
| **用户**   | 系统中的认证身份             | 登录名、账户       |

## 关系

- 一张**发票**只属于一位**客户**
- 一张**订单**会产生一张或多张**发票**

## 示例对话

> **开发者：** “**客户**下达**订单**时，我们会立即创建**发票**吗？”
> **领域专家：** “不会。只有确认**履约**后才生成**发票**。如果商品分成多个**货运批次**发出，一张**订单**可以产生多张**发票**。”
> **开发者：** “那么，如果某个**货运批次**在发出前被取消，就不会有对应的**发票**？”
> **领域专家：** “没错。**发票**的生命周期绑定于**履约**，而不是**订单**。”

## 已标记的歧义

- “账户”同时被用于表示**客户**和**用户**——两者是不同概念：**客户**下达订单，而**用户**是一个认证身份，可能代表也可能不代表某位**客户**。
```

## 规则

- **明确取舍。** 同一概念存在多个说法时，选出最佳术语，并将其他说法列为应避免的别名。
- **明确标记冲突。** 如果对话对某个术语的使用存在歧义，在“已标记的歧义”一节中指出，并给出清晰建议。
- **只包含与领域专家相关的术语。** 模块名或类名若不属于领域语言，则跳过。
- **保持定义紧凑。** 最多一句话。定义它*是什么*，而不是它做什么。
- **展示关系。** 使用粗体术语名称，并在关系明显时表达基数。
- **只包含领域术语。** 跳过通用编程概念（数组、函数、端点），除非它们具有领域特定含义。
- 出现自然分类时，**将术语分组到多个表格**中（例如按子领域、生命周期或参与者分类）。每组使用独立标题和表格。如果所有术语都属于同一个紧密领域，一个表格即可，不要强行分组。
- **编写示例对话。** 用开发者与领域专家之间 3–5 轮简短对话，展示术语如何自然配合。对话应澄清相关概念的边界，并准确使用术语。

## 示例对话

> **开发者：** “不使用 Docker 时，如何测试**同步服务**？”

> **领域专家：** “提供**文件系统层**而不是 **Docker 层**。它实现相同的**沙箱服务**接口，但使用本地目录作为**沙箱**。”

> **开发者：** “那么 **sync-in** 仍会创建一个**归档包**并将其解压？”

> **领域专家：** “没错。**同步服务**不知道自己在与哪一层交互。它调用 `exec` 和 `copyIn`，而**文件系统层**只是将它们作为本地 Shell 命令运行。”

</example>

## 再次运行

在同一对话中再次调用时：

1. 读取现有的 `UBIQUITOUS_LANGUAGE.md`
2. 纳入后续讨论中出现的新术语
3. 如果理解发生变化，更新定义
4. 标记新出现的歧义
5. 重写示例对话，纳入新术语
