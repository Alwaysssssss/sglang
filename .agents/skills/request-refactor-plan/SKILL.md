---

当用户希望创建重构请求时调用本技能。按以下步骤执行；如果某一步确实没有必要，可以跳过。

1. 请用户详细描述想解决的问题，以及任何潜在解决思路。

2. 探索仓库，验证用户的说法并了解代码库当前状态。

3. 询问用户是否考虑过其他方案，并向他们展示可选方案。

4. 围绕实现细节访谈用户，务必细致而全面。

5. 敲定实现的准确范围，明确计划修改与不修改的内容。

6. 在代码库中检查相关区域的测试覆盖。如果覆盖不足，询问用户的测试计划。

7. 将实现拆成由微小提交组成的计划。牢记 Martin Fowler 的建议：让每一步重构尽可能小，从而始终能看到程序正常运行。

8. 创建包含重构计划的 GitHub 议题。议题描述使用以下模板：

<refactor-plan-template>

## 问题陈述

从开发者视角描述其面临的问题。

## 解决方案

从开发者视角描述问题的解决方案。

## 提交

一份篇幅充分、细节完整的实现计划。使用清晰的中文编写，并将实现拆成尽可能小的提交。每次提交后，代码库都应保持可工作状态。

## 决策文档

列出已经做出的实现决策，可包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者给出的技术澄清
- 架构决策
- 数据结构变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段，它们很快就可能过时。

## 测试决策

列出已经做出的测试决策，包括：

- 什么样的测试才是好测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 可参考的现有测试（即代码库中的同类测试）

## 范围之外

描述本次重构范围之外的内容。

## 补充说明（可选）

关于本次重构的其他说明。

</refactor-plan-template>
