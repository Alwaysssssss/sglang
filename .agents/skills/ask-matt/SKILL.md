# 询问 Matt

不必记住每项技能，直接来问。

**流程**是一条穿过多项技能的路径。大多数路径沿一条**主流程**前进，另有两条**入口支线**汇入其中。其余技能要么独立使用，要么作为底层词汇层运行。

## 主流程：想法 → 交付

大多数工作都沿这条路线前进：你有一个想法，并希望把它构建出来。

1. **`/grill-with-docs`**——通过访谈打磨想法。**已有代码库**时从这里开始：它是有状态的，会把了解到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me`，参见“独立技能”。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 会留下文档轨迹。）
2. **分支——所有问题都能在对话中解决吗？** 如果某个问题需要通过可运行成果来回答（状态、业务逻辑、必须亲眼看到的界面），就绕道构建原型，并在往返两端使用 **`/handoff`** 衔接（参见“跨会话衔接”）：
   - 使用 **`/handoff`** 交出当前上下文，然后基于该文件开启全新会话；
   - 使用 **`/prototype`** 通过一次性代码回答问题；
   - 再用 **`/handoff`** 带回学到的内容，并在原始想法会话中引用它。
3. **分支——这是需要多个会话完成的构建吗？**
   - **是** → 使用 **`/to-spec`**（将会话整理成规格），再使用 **`/to-tickets`** 把它拆成曳光弹式工单，每张工单都声明自己的**阻塞边**。使用本地跟踪器时，每张工单对应 `.scratch/<功能>/issues/` 下的一个文件，人工按阻塞项优先的顺序处理；使用真实跟踪器时，边会变成原生阻塞链接，因此任何已解除全部阻塞的工单都可领取——针对每张工单启动 **`/implement`**，并在工单之间**清空上下文**。
   - **否** → 就在当前上下文窗口中使用 **`/implement`**。

   无论走哪条路径，**`/implement`** 都会在内部驱动 **`/tdd`**，一次完成一个红灯—绿灯切片；提交前再运行 **`/code-review`**，从规范和规格两个维度审查差异。如果只想以测试优先方式构建某个具体行为，而不需要完整规格，可单独使用 **`/tdd`**；如果想以某个固定点为基准审查分支或 PR，可单独使用 **`/code-review`**。

### 上下文卫生

让步骤 1–3 始终处于**同一个连续的上下文窗口**中——完成 `/to-tickets` 之前不要压缩或清空——使追问、规格和工单建立在同一套思考之上。之后每次 `/implement` 都从全新上下文开始，仅依据工单工作。

这一做法的上限是**[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口范围（当前先进模型约为 12 万 token）。如果会话在完成 `/to-tickets` 前已接近该上限，不要在能力退化后勉强推进；使用 `/handoff` 并在新会话中继续。

## 入口支线

这些起始情形会产生工作，之后再汇入主流程。

- **缺陷和请求不断堆积** → **`/triage`**。它让议题依次经过各分诊角色，产出可供智能体直接处理的议题，之后由 **`/implement`** 接手。

  分诊只用于**并非由你创建**的议题——缺陷报告、外部功能请求，以及任何未经整理的输入。`/to-tickets` 产出的工单已经可供智能体处理，**不要再次分诊**。

- **某处出故障** → **`/diagnosing-bugs`**。它适合棘手问题：初看无法解决的缺陷、间歇性失败，以及在两个已知正常状态之间悄然引入的回归。在建立**紧密反馈循环**前，它拒绝空谈理论——必须先有一条会因*当前缺陷*而变红的命令——随后用回归测试完成修复。如果复盘发现真正的问题是缺少能锁定缺陷的良好接缝，就交接给 **`/improve-codebase-architecture`**。

- **庞大而模糊的工作——全新项目或大型功能构建，一个会话无法容纳** → **`/wayfinder`**，这里认知负担最高的流程。当通往目标的道路尚不可见时，它会在议题跟踪器上绘制由**决策工单**组成的**共享地图**，逐一解决它们——产出的是**决策，而非交付物**——直到迷雾消退、路径清晰。**`/grill-with-docs`** 用来打磨一个会话能容纳的想法；探路者用于一个会话容纳不了的想法。它更慢、信息密度更高，因此只在真正需要时使用，绝不要用于边界清晰的功能。

  地图清晰后，**它负责交接，而不是构建**：在 **`/to-spec`** 处汇入主流程，将地图中相互链接的决策压缩成可构建计划，再照常执行 `/to-tickets` 和 `/implement`。从地图直接进入 `/implement` 会跳过压缩步骤并丢失关联细节；只有工作最终证明确实很小时，才可直接进入 `/implement`。

## 代码库健康

这里不是功能开发，而是日常维护。

- **`/improve-codebase-architecture`**——有空闲时就运行它，使代码库始终适合智能体操作。它会揭示**深化机会**；选中一个机会，就会*产生一个想法*，可从 `/grill-with-docs` 进入主流程。它负责勘察和发现候选项；下文的 **`/codebase-design`** 则是设计所选方案的工作台。

## 底层词汇

下面两个由模型调用的参考技能运行在其他技能*底层*，各自都是其词汇的唯一事实来源。当问题出在**用词**而不是流程时直接使用，也可让上层技能按需引入。

- **`/domain-modeling`**——打磨项目的*领域*语言：质疑含糊术语，解决一词多义（例如“账户”承担三种含义），并把难以逆转的决策记录为 ADR。`/grill-with-docs` 会主动运用这套纪律，使 `CONTEXT.md` 保持为干净的术语表。
- **`/codebase-design`**——用于设计模块*形态*的深模块词汇（模块、接口、深度、接缝、适配器、杠杆率、局部性）：在干净接缝处，以小接口隐藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 跨会话衔接

- **`/handoff`**——当会话已满或需要分叉出去（例如进入 `/prototype` 会话）时，将对话压缩成 Markdown 文件。不要留在原处继续，而应**开启新会话并引用该文件**，借此传递上下文。它是上下文窗口之间双向通行的桥梁。想使用**全新会话**但又需要**保留当前对话**时使用。
- **`/compact`**（内置）——留在**同一段对话**中，让早期轮次被总结。仅在**有意安排的阶段间断点**使用，也就是不介意丢失逐字历史的时候。不要在阶段中途压缩，否则智能体可能迷失方向。`/handoff` 用于分叉，`/compact` 用于延续。

## 独立技能

以下技能完全独立于主流程。

- **`/grill-me`**——执行与 `/grill-with-docs` 相同的不留情面访谈，但适用于**没有代码库**的情形。它是无状态的：不在本地保存任何内容，也不创建 `CONTEXT.md`。可用它打磨任何不属于仓库的计划或设计。
- **`/prototype`**——用一个小型的一次性程序回答单个设计问题：这种状态模型感觉是否正确，或界面应该是什么样子。从第一天起就把它当作一次性成果——保留答案，删除代码。它是主流程步骤 2 的绕行路线，也适用于任何难以在纸面确定的设计问题。
- **`/research`**——把资料阅读工作委派给**后台智能体**：它根据**一手来源**调查问题，然后在仓库中留下带引用的 Markdown 文件。它阅读时你可以继续工作。产出的文件应带入 `/grill-with-docs` 进入主流程——研究为思考提供素材，但不取代思考。
- **`/teach`**——使用当前目录作为有状态工作区，跨多个会话学习概念。
- **`/writing-great-skills`**——用于良好编写和编辑技能的参考。

## 前置条件

**`/setup-matt-pocock-skills`**——第一次运行工程流程前先执行它，配置其他技能所依赖的议题跟踪器、分诊标签和文档布局。也支持自定义议题跟踪器。
