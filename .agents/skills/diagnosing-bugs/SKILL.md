# 诊断缺陷

用于疑难缺陷的一套纪律。只有给出明确理由时才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如存在）以建立相关模块的清晰心智模型，并检查所改区域的 ADR。

## 阶段 1：建立反馈循环

**这就是本技能的核心。**其余工作都是机械执行。只要拥有一个能在*此缺陷*上变红的**紧密**通过/失败信号，就能找到原因；二分、假设检验和插桩都只是消费这个信号。没有它，盯着代码看再久也无济于事。

应在这里投入不成比例的精力。**积极尝试，发挥创造力，绝不轻易放弃。**

### 构建方式：大致按以下顺序尝试

1. 在能够触达缺陷的接缝处编写**失败测试**，可以是单元、集成或端到端测试。
2. 针对运行中的开发服务器编写 **Curl 或 HTTP 脚本**。
3. 使用夹具输入进行 **CLI 调用**，将标准输出与已知正确快照比较。
4. 编写**无头浏览器脚本**（Playwright 或 Puppeteer），驱动界面并断言 DOM、控制台或网络状态。
5. **重放已捕获的轨迹。**将真实网络请求、载荷或事件日志保存到磁盘，再隔离重放对应代码路径。
6. **一次性测试壳。**启动系统的最小子集，例如一个服务和模拟依赖，通过单次函数调用触发缺陷路径。
7. **属性或模糊测试循环。**如果缺陷表现为“有时输出错误”，运行 1000 组随机输入寻找失败模式。
8. **二分测试壳。**如果缺陷出现在两个已知状态（提交、数据集或版本）之间，自动执行“在状态 X 启动、检查、重复”，以便运行 `git bisect run`。
9. **差异循环。**让相同输入经过旧版本与新版本或两组配置，并比较输出。
10. **人在回路中的 Bash 脚本。**这是最后手段。必须由人点击时，使用 `scripts/hitl-loop.template.sh` 引导其操作，使循环仍保持结构化，并把捕获的输出反馈给智能体。

建立正确的反馈循环，就已经完成了 90% 的修复。

### 收紧循环

把循环当作产品。建立循环后继续将其**收紧**：

- 能否让它更快？例如缓存设置、跳过无关初始化、缩小测试范围。
- 能否让信号更敏锐？应断言具体症状，而不是“没有崩溃”。
- 能否让它更确定？例如固定时间、设置随机种子、隔离文件系统、冻结网络。

一个耗时 30 秒且不稳定的循环只比没有循环略好；一个耗时 2 秒且确定的循环才称得上紧密，是调试的超级能力。

### 非确定性缺陷

目标不是得到干净复现，而是获得**更高复现率**。将触发器循环 100 次、并行运行、增加压力、缩小时间窗口或注入等待。复现率 50% 的不稳定缺陷可以调试，1% 则不行；持续提高复现率，直到能够调试。

### 确实无法建立循环时

停止并明确说明情况，列出已尝试的方法。向用户请求：(a) 能复现问题的环境访问权；(b) 已捕获的产物，例如 HAR 文件、日志转储、核心转储或带时间戳的录屏；或 (c) 添加临时生产插桩的许可。没有循环时**不要**继续提出假设。

### 完成标准：能够变红的紧密循环

只有循环达到**紧密**且**能够变红**时，阶段 1 才算完成：必须给出**一条命令**，可以是脚本路径、测试调用或 Curl；该命令已经**至少运行过一次**，并附上调用及输出，而且满足：

- [ ] **能够变红** —— 驱动真实缺陷代码路径，并断言**用户描述的确切症状**，因此能在缺陷存在时变红、修复后变绿。仅仅“运行时不报错”不够，必须能*捕获这个具体缺陷*。
- [ ] **确定** —— 每次运行都给出相同结论；对于不稳定缺陷，按上文固定在较高复现率。
- [ ] **快速** —— 以秒计，而不是以分钟计。
- [ ] **智能体可运行** —— 可无人值守运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人在回路中参与。

如果在这条命令存在之前就开始阅读代码并构建理论，**立即停止。直接跳到假设正是本技能要防止的失败。**没有能够变红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，观察它变红并呈现缺陷。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好发生在附近的另一个失败。缺陷找错，修复也会错。
- [ ] 多次运行都能复现失败；对于非确定性缺陷，应达到足以调试的高复现率。
- [ ] 已捕获确切症状，例如错误消息、错误输出或缓慢耗时，使后续阶段能够验证修复确实解决了问题。

### 最小化

变红后，将复现场景缩小为**仍能变红的最小场景**。逐个删减输入、调用方、配置、数据和步骤，每次删减后重新运行循环，只保留对失败不可或缺的部分。

最小复现会缩小阶段 3 的假设空间，留下更少的可疑活动部件，并在阶段 5 转化为干净的回归测试。

当**每个剩余元素都不可或缺**时才算完成；删除任意一个都会让循环变绿。

在同时完成复现和最小化之前不要继续。

## 阶段 3：提出假设

测试任何假设前，先生成 **3–5 个排序后的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**，并明确写出它做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会使缺陷消失，或 <改变 Z> 会使问题加重。”

无法写出预测的假设只是感觉，应将其丢弃或继续收紧。

**测试前向用户展示排序列表。**用户常有能够立即改变排序的领域知识，例如“我们刚部署了第 3 项相关改动”，也可能知道哪些假设已被排除。这个检查点成本低，却能节省大量时间。不要因此阻塞；用户暂时不在线时按当前排序继续。

## 阶段 4：插桩

每个探针都必须对应阶段 3 的一个具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用**调试器或 REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界添加**定向日志**。
3. 绝不“记录所有内容再搜索”。

为**每条调试日志添加唯一前缀**，例如 `[DEBUG-a4f2]`。这样最后只需一次搜索即可完成清理。未标记日志保留，带标记日志删除。

**性能分支。**对于性能回归，日志通常不是正确工具。应先建立基线测量，例如计时测试壳、`performance.now()`、分析器或查询计划，再进行二分。先测量，后修复。

## 阶段 5：修复并添加回归测试

在修复**之前**编写回归测试，但前提是存在适合测试的**正确接缝**。

正确接缝能让测试按调用点中的实际形态驱动**真实缺陷模式**。如果唯一可用接缝过浅，例如缺陷需要多个调用方却只能测试单个调用方，或单元测试无法复现触发缺陷的调用链，那么在该处添加回归测试只会带来虚假信心。

**如果不存在正确接缝，这本身就是调查结论。**将其记录下来：代码库架构阻止了缺陷被测试锁定，并在下一阶段明确标记。

如果存在正确接缝：

1. 在该接缝处将最小复现转换为失败测试。
2. 观察测试失败。
3. 应用修复。
4. 观察测试通过。
5. 针对原始的未最小化场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理与复盘

声明完成前必须满足：

- [ ] 原始场景不再复现问题，已重新运行阶段 1 循环；
- [ ] 回归测试通过，或已记录缺少正确接缝；
- [ ] 已删除所有 `[DEBUG-...]` 插桩，可搜索前缀确认；
- [ ] 已删除一次性原型，或移动到明确标记的调试位置；
- [ ] 已在提交或 PR 消息中写明最终证实的假设，使下一位调试者能够复用结论。

**然后追问：怎样才能预防这个缺陷？**如果答案涉及架构改动，例如缺少良好测试接缝、调用方纠缠或隐藏耦合，则携带具体情况交给 `/improve-codebase-architecture` 技能。应在修复完成**之后**提出建议，而不是之前；此时掌握的信息远多于开始时。
